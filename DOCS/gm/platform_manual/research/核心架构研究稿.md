# GM 平台核心架构与运行时数据流研究稿

> 用途：供最终《GM 平台技术说明书》引用。本文依据当前活动源码、正式合同与 Generation 09 封存证据整理，不是概念设计稿，也不把测试夹具当作产品入口。
>
> 当前已验证基线：Godot `4.6.2-stable official`；`4.7.2-stable` 只是未执行的未来兼容实验目标。P27 封存结论为 `P27_SEALED_GENERALIZED_WITH_AP3_RISKS`。证据见 `reports/gm/p27/active_reviewer_final_seal.md`。

## 1. 核心结论

GM 的运行时不是“场景脚本直接改一切”的框架，而是一组可组合、可裁剪、失败关闭的合同层：

1. `GMModuleManifestIndex` 和 `GMModuleManifest` 描述可用模块、依赖、冲突、服务、空间后端及导出边界；`GMModuleRegistry` 负责验证和拓扑解析。
2. `GMRuntimeContext` 按拓扑顺序安装服务，并保证一个 SceneContext 只能激活一个空间执行后端。
3. 玩家、AI、日程、事件和调试入口最终都应产生统一的 `GMAbilityActivationRequest`，再由 `GMAbilitySystemHost` 执行能力生命周期。
4. 会改变领域事实的动作必须进入 `GMDomainResolver` + `GMDomainTransactionCoordinator`，经过预检、预留、提交、回滚/恢复，成功后才原子地产生 `FactEvent + ChangeRecord + Cue` 提交包。
5. `GMSimulationWorld` 是后台世界的单一聚合根；系统只读 `GMWorldSnapshot`，向 `GMCommandBuffer` 写意图，由世界确定性合并并提交。
6. `GMStore` 保存领域纯数据；UI、查询结果、节点、RID、导航对象和派生缓存都不是权威。
7. 保存恢复采用“完整离线验证、最后一次无失败交换”的原子边界。扩展状态通过 contributor 的 `prepare/commit` 接入，不得旁路另建第二存档根。
8. 2D 与 Planar3D 共享逻辑平面合同 `GMPlanarPosition` / `GMSpatialTargetRef`；Planar3D 是 Surface Graph 上的平面语义投影，不是任意 Full 3D 游戏逻辑。
9. 角色 VisualRecipe 和地图/角色编译缓存只负责表现构建；Recipe/Content 与世界事实才是权威，缓存必须可删可重建。

## 2. 项目入口与启动顺序

### 2.1 平台级入口

- `project.godot`：Godot 工程设置和默认主场景来源。
- `gm_runtime/gm_platform.gd`：平台版本、Godot 基线、插件锁和环境报告的只读校验入口；关键方法为 `validate()`、`environment()`、`plugin_report()`、`compatibility()`。
- `gm_runtime/gm_minimal_entry.tscn` / `gm_runtime/gm_minimal_entry.gd`：最小平台入口。
- `gm_runtime/vertical_sample/gm_ext_3d_11_entry.tscn`：当前 Planar3D 正式纵向入口。
- `gm_runtime/vertical_sample/gm_ext_3d_11_2d_entry.tscn`：严格 2D-only 正式入口。
- `gm_runtime/player_shell/gm_p25_player_shell.tscn` 与 `gm_runtime/player_shell/gm_p25_2d_only_delivery.tscn`：PlayerShell 完整/2D-only 组合入口。

开发者不应从 `tests/`、`reports/`、旧 `gm_p18_*` fixture 或 `*_export_entry` 验证场景搭建正式游戏。正式入口与导出裁剪由 Profile、Manifest Index 和 Export Planner 共同决定。

### 2.2 PlayerShell 的实际启动序列

`gm_runtime/player_shell/gm_player_shell.gd::_ready()` 的顺序是：

```text
解析 GMPlayerShellConfiguration
  -> 2D-only 时切换 GM_MODULE_INDEX_PATH
  -> 注册输入映射
  -> _build_runtime()
  -> 构建正式 HUD
  -> 若配置/命令行要求，则 restore_world_snapshot()
  -> 刷新只读投影
  -> 仅在合同模式下调度自动检查
```

关键点：恢复发生在 Runtime、语义地图、Player、Task、SceneSession、SimulationWorld 和 Store 已建立之后。P27 曾修复“2D 文件创建但新进程不加载”的问题，不能把恢复提前到贡献者未装配阶段。

配置入口为 `GMPlayerShellConfiguration`（`gm_runtime/player_shell/gm_player_shell_configuration.gd`）：

- `load_for_id()`：从 `res://gm_runtime/player_shell/configurations/` 加载配置。
- `validate()`：验证 Project/Profile/地图/角色/任务/交互/存档字段。
- `to_native()`：输出纯数据组合记录。
- `configuration_id_from_args()`：支持命令行选择配置。

## 3. 模块注册、依赖与服务生命周期

### 3.1 Manifest 数据模型

`gm_runtime/gm_module_manifest.gd` 的 `GMModuleManifest` 是模块声明权威，主要字段包括：

- 身份：`module_id`、`version`、中文名称/说明。
- 依赖：`required_modules`、`optional_modules`、`conflicts`。
- 内容面：`content_types`、`abilities`、`effects`、`events`、`cues`、`tags`。
- 服务面：`runtime_services`、`runtime_service_implementations`、`service_specs`。
- 空间面：`spatial_backends`。
- 编辑器/导出面：`editor_entries`、`export_required_paths`、`export_excluded_paths`。
- 运维面：`validation_rules`、`migrations`、`release_security_profile`、原生依赖与私有构建物。

`schema_errors()` 会拒绝空/重复 ID、自依赖、未知引用、重复服务以及无效空间后端声明。Manifest Index 由 `gm_runtime/gm_module_manifest_index.gd` 表示，正式 Planar3D 组合见 `gm_runtime/manifests/gm_ext_3d_11_manifest_index.tres`。

当前 Planar3D 组合包含：

```text
core
spatial.core
spatial.planar_2d
spatial.planar_3d
character.visual_3d
scene.execution
presentation.render_style_3d
sample.neutral_vertical
```

严格 2D-only Index 只包含 `core + spatial.core + spatial.planar_2d`，见 `gm_runtime/manifests/gm_ext_3d_11_2d_manifest_index.tres`。

### 3.2 解析和安装

典型调用：

```gdscript
var resolution := GMModuleRegistry.resolve(profile.enabled_modules)
if not resolution.ok:
    return resolution
var context := GMRuntimeContext.new()
var installed := context.install(PackedStringArray(resolution.selected))
```

核心方法：

- `GMModuleRegistry.refresh_result()`：构造并提交当前 Registry 快照。
- `resolve(selected)`：解析所选模块及必需依赖。
- `topological_order(selected)`：返回确定性安装顺序。
- `validate_explicit(selected)`：检查调用方是否显式给足必需模块。
- `manifest_contract()` / `spatial_backend_contract()`：向运行时和导出器公开已验证合同。
- `GMRuntimeContext.install()`：先预检所有服务，再实例化/初始化；任一失败会回滚本次新增服务。
- `GMRuntimeContext.release()`：逆安装顺序 shutdown，并断开由 Context 管理的信号。

Registry 有 `registry_generation`。Context 已装载旧代时，不能悄悄切到新代，必须先 `release()`。服务 ID 全局不可重复；实现应通过 `GMServiceSpec` 或 Manifest 映射声明，不要在业务脚本里扫描目录并自行 new 一个同名服务。

### 3.3 扩展模块的正确做法

1. 新建一个稳定 `module_id` 的 `.tres` Manifest。
2. 写全必需依赖、服务、导出 required/excluded paths 和验证规则。
3. 将 Manifest 路径加入项目自己的 Manifest Index。
4. 用 `GMModuleRegistry.resolve()` 验证闭包和冲突。
5. 服务实现提供 `initialize(context)` / `shutdown()`（需要时），通过 `GMRuntimeContext` 生命周期管理。
6. 空间模块额外声明 `GMSpatialBackendDeclaration`，运行时能力集合必须和 Manifest 完全一致。

禁止：覆盖 `GMModuleRegistry` 快照、跳过 Manifest 直接激活未声明后端、重复服务 ID、在已有运行时中热换 Registry 代际、把 editor/tests/reports 打入正式包。

## 4. 空间合同：2D、Planar3D 与 Surface Graph

### 4.1 逻辑位置和目标

`GMPlanarPosition`（`gm_runtime/spatial_core/gm_planar_position.gd`）是 2D/Planar3D 共用值：

```json
{
  "schema_version": 1,
  "map_id": "gm.map.example",
  "surface_id": "gm.surface.example.ground",
  "x": 12.5,
  "y": 8.0
}
```

它明确不包含 Scene、Node、Navigation、Backend 实例。`GMSpatialTargetRef` 支持 `entity`、`anchor`、`route`、`facility_slot`、`logical_position`；稳定语义目标不得同时夹带自由坐标。

`GMSpatialDomain` 声明：

- `gm.spatial.planar_2d`
- `gm.spatial.planar_3d`
- `gm.spatial.full_3d_reserved`（保留，未提供通用执行能力）

### 4.2 后端激活与查询

`GMRuntimeContext.activate_spatial_backend()` 会：刷新 Manifest 合同、确认 backend/domain/capabilities、加载实现、注册后端，并拒绝同一 Context 的第二个活动后端。查询统一走：

```gdscript
context.query_spatial(capability_id, method_name, arguments)
```

返回必须通过 `GMSpatialQueryResult.validate_native()`，失败使用结构化 blocked reason，不能让后端返回任意对象。

Planar3D Manifest `gm_runtime/manifests/spatial_planar_3d.tres` 声明 Surface Graph 能力，包括目标解析、逻辑/世界坐标转换、平面距离/方向、旅行成本、Surface 查找/吸附、可达性与寻路、屏幕转换等。实现为 `gm_adapters/spatial3d/gm_planar_3d_spatial_adapter.gd`；图数据在 `gm_runtime/map/3d/gm_surface_graph.gd`、`gm_surface_definition_3d.gd`、`gm_surface_connection.gd`。

保存时只保存逻辑位置和已创作 Graph 状态，不保存 `NavigationAgent`、`NavigationRegion` 或后端对象。`GMSimulationWorld.register_entity()` 和 `set_entity_spatial_position()` 会先通过活动后端确认 Surface。

### 4.3 2D/Planar3D 双投影

PlayerShell 的 `set_dimension()` 会切换 Camera/Query 投影，并通过 `_activate_context_backend()` 清理旧后端、激活目标后端。它不应改变 Task、Fact、Store 或业务实体身份。2D-only 交付调用 3D 会得到 `delivery.3d_module_excluded`，而不是回退加载 3D。

开发者扩展地图时应创作稳定 `map_id/surface_id/anchor_id/route_id/facility_slot_id`，并让两种后端映射同一逻辑意义；不要以 NodePath、场景树层级或世界坐标作为业务身份。

## 5. PlayerShell：玩家操作的组合层，不是第二权威

`GMPlayerShell` 负责输入、正式 HUD、2D/3D投影、交互查询和各权威服务的组合。常用公开方法：

- `handle_action(action_id, data)`：统一正式动作入口。
- `drive_direction()` / `advance_simulation()`：移动输入和确定性推进。
- `query_active_target()` / `interact_with_key()`：空间查询后发交互请求。
- `assign_task()`：经 `GMInteractionRouter` 提交 Task 交互。
- `switch_scene()`：启动/切换 `GMTaskExecutionSession`。
- `set_dimension()`：只切表现/空间查询后端。
- `save_world_snapshot()` / `restore_world_snapshot()`：委托 SimulationWorld。
- `task_projection()` / `snapshot()`：供 UI 读取，不拥有任务事实。

输入映射使用 `gm.p25.*` 动作；键鼠与手柄最后都进入 `dispatch_input_event()` → `handle_action()`。UI 显示应读取投影，不能直接改 Task/对象/Store。

## 6. Task、Planner、Movement、Interaction 与 Scene 执行

### 6.1 Task 权威

`GMTaskService`（`gm_runtime/tasks/gm_task_service.gd`）是 Task 域权威：

- Store：`gm.store.task_domain`
- Store schema：`gm.task.domain.v3`
- Snapshot：`gm.task.snapshot.v3`
- Task 状态：`draft → available → assigned → in_progress/blocked → completed/failed/cancelled`
- Assignment：`active/revoked/rejected`
- Reservation：`active/released/consumed/expired`

写操作从 `submit_operation(host, operation, payload, source_type, source_id, idempotency_key)` 进入统一 Ability/Transaction 管线。支持定义/分组/发布/分配/替换/撤销/拒绝/状态迁移、Provider/Duty、Reservation 和逻辑时钟。`read_task()` 等读取返回副本。

目标进度不接受 UI 自报成功；`consume_committed_signal()` 会从权威 `GMCommittedFactResult` 或提交包解析信号、校验因果身份并生成 signal receipt。Planner 恢复也会回读 Task/Assignment/Reservation，拒绝陈旧权威。

### 6.2 Planner

`GMAgentPlanner` 输入严格的 `gm.agent.context.v1`，候选只能是 Task 或 FreeAction。它按：

```text
hard_priority（降序）
  -> 固定点 score_units（降序）
  -> Task 优先于 FreeAction
  -> candidate_id 字典序
```

输出 `gm.execution_plan.v2` 和 `gm.decision_receipt.v2`。评分采用 `gm.planner.numeric.fixed.v1`、12 位固定小数和 JSON 安全整数，贡献项固定为 source_duty、urgency、skill_tags、preference、distance、resource_availability、fatigue、risk、interrupt_cost、schedule，再加显式 seed offset。

`GMAgentPlannerRuntime` 通过 `GMActivationPolicy` 控制 mounted、active、player_takeover、blocked 等生命周期；首次决策必须有显式 mounted/context_valid 事件。`GMPlanBehaviorAdapter.submit()` 只把计划翻译为角色公开 Ability 请求；移动计划转成 `GMMovementRequest`，不自行移动节点。

### 6.3 Movement

`GMMovementAbilityExecutor` 的典型序列：

```text
register_actor(actor_id, Node2D, map_id)
  -> preflight(request, actor)
  -> start_request(request, actor)
  -> tick_command(command_id, delta) 多次
  -> 成功 / cancel_move / 结构化失败
```

它检查控制权、数值有限性、地图可走性、目标/路径事实、版本和恢复快照。`GMTravelHandoff.build()` 将跨场景移动转换为稳定交接值，随后可由 `GMTaskExecutionSession.open_from_travel_handoff()` 使用。移动表现语义可以写入 Actor 投影，但位置/目标/路径权威不能藏在动画节点中。

### 6.4 Interaction

`GMInteractionRouter` 支持 `ability/task/transaction/process` 四种 kind。调用：

```gdscript
router.register_backend("ability", ability_backend)
var request := GMInteractionRequest.ability(...)
var result: GMInteractionResult = router.submit(request)
```

Router 校验纯值请求、按 kind 找 Backend，再校验结果中的 request/interaction/kind 身份一致性。Backend 缺失必须失败关闭，不能绕路调用另一套实现。

对象交互的完整例子在 `gm_runtime/objects/gm_object_ability_host_node.gd`：从对象 Definition 解析 InteractionRecipe，预检对象状态，构造稳定幂等键与 `GMAbilityActivationRequest`，再由 Host 激活。真正领域写入由 `GMObjectInteractionService` 执行事务预检/预留/提交/回滚；对象状态修改成功后才产生 Fact/Change/Cue。

### 6.5 Scene/任务执行会话

`GMSceneRecipeBuilder.build()` 把 SceneRecipe、Skeleton、TaskExecutionContext 与空间 Backend 解析为稳定 build artifact；`GMTaskExecutionSession` 管理进入、事实记录、领域请求结算、撤离/返回/失败/暂停/恢复/关闭。

典型调用：

```text
GMTaskExecutionSession.open(definition, builder, backend)
  -> session.start()
  -> record_domain_request(request)
  -> settle_domain_request(committed_or_blocked_result)
  -> record_fact(...)
  -> request_return() / request_extraction() / fail()
```

Snapshot schema 是 `gm.scene.session_snapshot.v1`。恢复使用 `prepare_snapshot()` 后 `commit_prepared_snapshot()`；Definition 指纹、Fact/Request 关系、目标完成度和 travel handoff 都必须一致。

## 7. Ability、Resolver、Transaction、Fact、Change 与 Cue

### 7.1 统一请求与 Host

`GMAbilityActivationRequest` 明确规定所有输入、AI、日程、调试器和事件触发都构造同一请求。关键字段：Ability ID/Tag、TargetData、event_data、source、schedule_context、request_id、idempotency_key 和 causal_chain。

推荐最小模式：

```gdscript
var request := GMAbilityActivationRequest.new(
    host,
    "gm.ability.example",
    "",
    target_data,
    {"source_id": actor_id, "target_id": target_id},
    "gm.source.player",
    {},
    "example.operation.000001"
)
var result := host.activate_typed(request)
```

显式幂等键是精确材料：大小写、空白、Unicode 与分隔符不会被自动归一化；不得包含 NodePath、`res://` 或 `user://`。Host 用它分配 `gm.ability.instance.v2.*` 稳定实例，并检查同键请求合同是否相同。

`GMAbilitySystemHost` 提供 mount/unmount/dispose、定义注册与 grant/revoke、Scheduler、Tag/Attribute/Effect/Cue、能力检查/prepare/commit/rollback/finalize、快照恢复等。能力执行若会改变领域事实，Definition 应声明 resolver/service/fact_type，走 `execute_domain_transaction()`。

### 7.2 领域事务序列

`GMDomainTransactionCoordinator.resolve()` 的真实顺序：

```text
校验 request/resolver/stores/causal chain/稳定身份
  -> 幂等 Fact / reward receipt 查重
  -> 建立 Request -> AbilityInstance -> Resolver -> Transaction 因果前缀
  -> 预演 Fact/Change/Cue 后续链接
  -> capture_transaction_state（恢复点）
  -> resolver.preflight_transaction
  -> resolver.reserve_transaction
  -> resolver.commit_transaction
  -> 构造 FactEvent、ChangeRecord、Cue 引用
  -> FactEventStore.append_committed（原子提交包）
  -> transaction.mark_committed / resolver.finalize_transaction
  -> 从同一权威提交包返回 GMCommittedFactResult
```

任一步失败都会 `_finish_failure()`：先普通 rollback，再释放预留；若失败则从恢复点强制恢复；仍失败则隔离 Resolver，禁止继续正常事务。自定义 Resolver 必须实现：

- `preflight_transaction`
- `reserve_transaction`
- `commit_transaction`
- `rollback_transaction`
- `capture_transaction_state`
- `restore_transaction_state`
- `release_transaction_reservations`
- `isolate_transaction_state`
- 可选 `finalize_transaction`、`version_for`、`build_candidate`

### 7.3 三类输出的边界

- `GMFactEvent`：已经提交的领域事实；只有 Coordinator 持有的内部 capability 才能 `mark_committed()`。普通 GameplayEvent 不是事实。
- `GMChangeRecord`：与 Fact/Transaction/因果链关联的 before/after 变更记录；用于审计，不是另一份可写世界。
- `GMCueParameters` / `GMCueRouter`：表现语义。Cue 可以记录和通知，不能修改规则事实。

`GMFactEventStore.append_committed()` 会把 Fact、Changes、Cues 和 CausalChain 固结为可验证提交包。重复幂等键只有在身份和业务材料相同才返回既有结果；不同请求复用同键会被拒绝。

## 8. Process：持续行为的通用生命周期

`GMProcessDefinition` 描述 definition_id、revision、family、duration_units、capability_ids、稳定 Facility/WorkSpot 目标、completion kind/payload 以及可选 Task/Duty 关联。Process 只能引用稳定语义目标；不能在定义中保存自由坐标。

`GMProcessService.request()` 只接受 `gm.ability.process.*` 请求和显式幂等键。支持：`start`、`participate`、`pause`、`resume`、`cancel`。实际推进由 `advance(instance_id, units)` 使用 `GMProcessClock`；完成后经 `GMProcessSettlementGateway` 结算，再把运行态与时钟一起持久化。

状态图：

```text
created -> ready -> running -> completed
             |        |  \
             |        |   -> blocked -> running（显式 retry）
             |        -> paused -> ready/running
             -> paused
任一非终态可 cancel/fail；failed 可显式 recover 到 ready
```

`GMProcessService.restore_snapshot()` 先在新 Store/Clock 中完整验证，然后替换引用。完成结算不能由 Process 内核直接伪造 Fact；领域含义留给 gateway/resolver。

## 9. SimulationWorld、CommandBuffer 与单一世界权威

`GMSimulationWorld` 的 Tick 数据流：

```text
capture_snapshot()
  -> 按 stage、priority、system_id 排序运行 GMSimulationSystem
  -> 每个系统只读 GMWorldSnapshot，写自己的 GMCommandBuffer
  -> 系统失败只隔离自己的 buffer
  -> merge_command_buffers() 校验 snapshot、幂等键、write_keys 冲突、预算
  -> commit_merge()
  -> state_patch / set_resolution / abstract / domain
  -> 生成 commit receipt 与 post-receipt mutation journal
```

世界中的权威组件是 EntityRegistry、Event/Change Store、命名 Store、提交收据、抽象提交、Scheduler debt 等。`GMWorldSnapshot` 是深拷贝只读值，包含 `gm.world_snapshot.v2`、内容摘要和 `snapshot_id`；修改读取到的 `entities/world_state` 不会回写快照。

自定义后台系统应继承/遵循 `GMSimulationSystem`，只产生声明了 snapshot_id、entity_id、resolution、expected_version、write_keys、idempotency_key 的命令。不要在 System 的 `run()` 里直接改 Registry、Store 或场景节点。

## 10. GMStore、保存恢复、schema 与 contributor

### 10.1 Store 合同

`GMStore` 的快照 schema 是 `gm.store_snapshot.v3`。`put()` / `erase()` 支持 expected_version 乐观并发，写入仅接受持久化纯数据；key 必须是稳定业务身份，不能是路径。索引是 records 的派生投影，恢复时必须与 records 完全一致，不会静默“修好”损坏索引。

### 10.2 世界文件

当前世界文件 schema 为 `gm.simulation_world.v6`；正式发布声明见 `gm_runtime/vertical_sample/gm_planar3d_release_contract.gd::migration_declaration()`。当前只承诺 v6 → v6、Store v3 → v3；`migration_required=false`，旧 world v2/v3/v4 必须由原兼容版本重导，不能假称自动迁移。

`GMSimulationWorld.save_snapshot()` 包含精确顶层字段：world_id、seed、tick、phase、budget、registry、event_store、stores、abstract_commits、commit_receipts、post_receipt_journal、pending_merge、scheduler_debt、tick_history，以及可选 spatial_state。

### 10.3 原子恢复

`GMAtomicWorldLoadCoordinator.load()` 的原则是：

1. 校验精确 schema、字段形状、world_id、纯数据。
2. 在 detached Registry/EventStore/ChangeStore/Stores 中恢复并验证。
3. 校验 Store 集合和索引、收据账本、journal 与最终投影。
4. 校验空间 Graph 与暂存实体位置。
5. 调用所有 contributor 的 prepare，在不修改 live object 的情况下产出 prepared state。
6. 所有验证通过后才交换 world 引用、值和 contributor 状态。

扩展保存状态应调用：

```gdscript
world.register_atomic_restore_participant(prepare_callback, commit_callback)
```

`prepare(snapshot, staged_stores)` 必须只验证和构造 detached 候选，返回 `{"ok": true, "prepared": ...}`；`commit(prepared, world)` 必须是无失败赋值/交换。PlayerShell 示例见 `_capture_p25_contributors()`、`_prepare_p25_contributors()`、`_commit_p25_contributors()`：Task 权威、Player、Object、SceneSession 先进入同一个 `gm.store.player_shell`，再由世界存档统一持久化。

禁止：另写第二个 JSON 保存根、恢复一半后再校验、把 Node/RID/NodePath/缓存路径放进存档、忽略 world/store/profile 身份不匹配、在坏输入失败后留下部分修改。

## 11. 稳定身份与纯数据规则

稳定身份是跨进程、存档、Profile 和 2D/3D 对应的基础：

- 实体使用 `gm.entity.*`（`GMEntityId`）。
- Ability 实例使用 `gm.ability.instance.v2.*`，由 Host 分配。
- 事实/变更使用 `gm.fact.v2.*` / `gm.change.v2.*`。
- 地图、Surface、Anchor、Route、Facility、Profile、Recipe、Task、Assignment、Reservation 都应使用稳定小写业务 ID。
- ID 不得是 NodePath、绝对路径、`res://`、`user://`、RID 或运行时实例号。

`GMStableData.validate_persistence()` / canonical/digest 是多数公共合同的共同边界。开发者自定义 Dictionary 时应使用字符串键、JSON 安全整数、有限浮点和嵌套纯值；避免依赖 Dictionary 插入顺序。

P27 特别验证了非默认 Profile：新增 actor/entity ID 必须从目标 Profile 的 namespace 派生，不能硬编码 `ext3d10`；显式目标缺失/类型错误必须失败关闭，不能回退写默认资源。

## 12. VisualRecipe、编译缓存、地图构建与表现预算

### 12.1 角色 VisualRecipe

`GMCharacterVisualRecipe`（schema `gm.character.visual_recipe.v1`）只保存稳定 Content ID：Body、Head、Hair、Outfit、Feature、Accessory、Posture、Skeleton、Animation Profile、Palette 等。它明确不保存 Node、Node3D、RID、AnimationPlayer 或 PackedScene。

使用序列：

```text
GMContentLibrary.scan(content_roots)
  -> GMCharacterVisual3DResolver(library)
  -> recipe.validate_recipe()/validate_against(index)
  -> GMCharacterVisualCompileCache.get_or_compile(recipe, resolver)
  -> GMCharacterAssembler3D.assemble/configure
```

`GMCharacterVisualCompileCache` 的 authority 字段始终是 `VisualRecipe`、`cache_authority=false`。缓存键由 Recipe 与所有依赖资源指纹决定；变更后 `invalidate_changed()`，也可 `delete()` / `clear()` / `rebuild()`。缓存丢失必须能从 Content + Recipe 重建。

### 12.2 地图/场景 Recipe 缓存

`GMSceneBuilder3D` 从 SceneRecipe、Skeleton、Context、Surface Graph、Facility Visual Profile 与 placements 构建 Node3D 表现。`GMSceneRecipeCompileCache` 默认写派生 artifact，使用 source digest、cache key 与 latest identity；其 `delete_cache()` 说明该层同样不是世界权威。

### 12.3 视觉预算

`GMCharacterVisualBudgetProfile` 是项目可配置表现预算，默认值包括：Near 12、Far 32、最多动画角色 30、完整质量 10、SkinnedMesh 60、每帧动画更新 20、Feature 20、动画预算 4ms、世界视口 640×360。

`GMVisualBudgetManager3D` 按相机距离、可见性和滞回分配 Near/Mid/Far/Offscreen；超预算时降 LOD、暂停部分皮肤/Feature 或保留最后姿态。它只调度表现，不得改变世界逻辑。旧采样最久者优先，避免尾部角色永久饥饿。

## 13. 单一权威边界速查

| 领域 | 权威 | 允许的投影/派生物 | 绝对不能成为第二权威的内容 |
|---|---|---|---|
| 模块 | Manifest + Registry committed snapshot | 编辑器列表、导出计划 | 目录扫描结果、手工 service map |
| 世界 | GMSimulationWorld / EntityRegistry | SceneBridge、HUD、渲染节点 | 场景节点状态、相机、导航对象 |
| Task | GMTaskService + task Store/Fact | TaskProjection、HUD | Dock 字段、Planner 当前显示 |
| 能力事实 | Resolver commit + FactEventStore 提交包 | Change 审计、Cue 表现 | GameplayEvent、动画完成回调自报事实 |
| Process | GMProcessStore + Clock + Settlement | 进度 UI、Feedback | 进度条节点、Timer 实时时间 |
| 空间 | GMPlanarPosition + authored map/Surface Graph | 2D/3D 世界坐标与查询结果 | Transform、NodePath、NavigationAgent |
| 角色表现 | VisualRecipe + GMContentLibrary | CompileCache、装配节点、LOD | 缓存 artifact、MeshInstance 状态 |
| 保存 | SimulationWorld world file + named GMStores | 临时 staged candidate | 第二 JSON 根、UI/cache 快照 |

## 14. 开发者搭建新游戏的推荐主链

1. 定义项目自己的 Profile、稳定命名空间和 `user://` 存档路径。
2. 选择 2D-only 或 Planar3D-enabled Manifest Index，不要混装后再运行时隐藏。
3. 建立地图、Surface/Anchor/Route/Facility 语义资源。
4. 用 ContentLibrary 注册对象、角色、视觉 Recipe、任务和 Process 定义。
5. 用 `GMRuntimeContext.install()` 安装模块服务并激活唯一空间后端。
6. 装配 `GMSimulationWorld`、命名 Store、Resolver 和 contributor。
7. 玩家/AI/日程全部通过 Interaction/Ability 请求；领域改变通过 Transaction 提交。
8. UI 只读取 Projection/Snapshot/Committed Result。
9. 对保存做至少三种验证：无存档首启、保存退出后独立新进程恢复、损坏/异项目存档原子拒绝。
10. 对非默认 Profile 再跑一次完整编辑器退出与独立进程读取，防止默认身份/路径硬编码。

## 15. 已知限制和审查边界

- 当前正式实跑版本仅 Godot `4.6.2-stable official`。
- `FULL_3D_RESERVED` 不是已实现的 Full 3D 游戏逻辑；Planar3D 是逻辑平面 + Surface Graph + 3D 表现。
- `DN-01`：发布附加记录外层/内层 surface 不一致仍可能被接受，尚未证明影响实际玩法权威。
- `DN-02`：退出时存在 ObjectDB/resources-in-use 诊断警告，当前未观察到运行期增长、存档损坏或启动失败。
- `TN-01`：历史审查夹具/编排曾修正，不能引用旧失败/旧通过替代当前入口证据。
- HX1 为 `HX1_RETIRED_PLATFORM_INCOMPATIBLE`，不是 PASS；8 组 GUI/真人交互仍需最终人工验收。程序化控件和非 headless 测试不能冒充真人策划盲测。
- 任何对冻结核心、Profile/入口、模块选择、身份或保存隔离的修改，都应重新做受影响面复审；不能继续沿用 P27/CAW 封记。
