# GM 平台构建、裁剪、验证与独立项目复制研究稿

> 文档性质：面向游戏项目开发者与构建/发布工程师的技术研究稿。本文基于当前工作区实际源码、`project.godot`、`export_presets.cfg`、模块 Manifest、P27/AP3 封存材料和已验收 CAW 复制实例整理。它描述的是当前已验证边界，不把未来目标或真人 GUI 验收写成已通过能力。

## 1. 结论先行

GM 当前可以作为 Godot 4.6.2 的模块化游戏底座交付，正式发布有两种互斥模式：

| 模式 | 模块集合 | 正式入口 | P27 preset | 已封存合同 |
|---|---|---|---|---|
| `2D-only` | `core`、`spatial.core`、`spatial.planar_2d` | `res://gm_runtime/vertical_sample/gm_ext_3d_11_2d_entry.tscn` | `GM_P27_2D_Only_Debug` / `GM_P27_2D_Only_Release` | 9/9 |
| `Planar3D-enabled` | 上述三项，加 `spatial.planar_3d`、`character.visual_3d`、`scene.execution`、`presentation.render_style_3d`、`sample.neutral_vertical` | `res://gm_runtime/vertical_sample/gm_ext_3d_11_entry.tscn` | `GM_P27_Planar3D_Enabled_Debug` / `GM_P27_Planar3D_Enabled_Release` | 13/13 |

两种模式不能隐式合并。`Planar3D-enabled` 是在二维逻辑坐标和权威数据层上增加平面化三维呈现，不等于完整 Full3D；`gm.spatial.full_3d_reserved` 仍是保留域，不是本轮允许的发布能力。

发布的最小闭环不是“编辑器能运行”或“导出成功”，而是：

1. Profile 与模块索引可解析；
2. 依赖扫描和导出规划无越界；
3. Debug、Release、PCK 都从同一源码状态生成；
4. 正式入口实际启动；
5. 模块合同、包清单、存档/恢复和原子拒绝通过；
6. 候选大小、摘要、magic、入口与源码对应关系写入机器清单；
7. 若复制到独立游戏项目，必须再建立新的项目身份、Profile、`user://`、Store 和缓存边界，并接受独立复审。

## 3. 工程、入口与插件

### 3.1 Godot 工程基线

当前 `project.godot` 声明：

- 工程名：`GameMaker Platform Lab`；
- Godot feature：`4.6`；
- 默认入口：`res://gm_runtime/gm_minimal_entry.tscn`；
- 渲染器：`gl_compatibility`；
- 窗口基准：1100×700；
- P27 正式入口通过 preset 覆盖，不依赖默认入口。

已验证引擎是 `4.6.2.stable.official.71f334935`。`4.7.2-stable` 只是未执行的未来兼容实验目标。开发者升级引擎前必须建立独立兼容分支并重跑完整合同，不能把当前封存结论外推到 4.7.2。

### 3.2 编辑器插件与发布依赖不是一回事

当前工程启用六个编辑器插件：

- `gm_editor`
- `gm_agent_planner`
- `TileMapDual`
- `gut`
- `gm_feedback`
- `gm_p26_vertical_sample`

但 P27 正式包使用 `exclude_filter="addons/*,..."`，实际 release-runtime required 列表为空。GUT 9.6.1 / MIT 是开发和测试依赖；TileMapDual v5.0.2 / MIT 及 Dialogue Manager、State Charts、LimboAI、Aseprite Wizard 都不属于本次正式递归依赖图。不要因为插件在编辑器中启用，就把它标成运行时必需。

## 4. 模块系统和两种发布选择

### 4.1 Manifest/Index 工作方式

模块索引只保存 Manifest 路径，`GMModuleRegistry.resolve()` 负责解析依赖并得到 `selected`；`manifest_contract()` 再形成可审查的模块版本和路径合同。当前两套索引版本均为 `1.0.0`。

Planar3D 模块版本：

| 模块 | 版本 |
|---|---|
| `core` | 1.0.0 |
| `spatial.core` | 1.0.0 |
| `spatial.planar_2d` | 1.0.0 |
| `spatial.planar_3d` | 1.0.0 |
| `character.visual_3d` | 1.0.0 |
| `scene.execution` | 1.0.0 |
| `presentation.render_style_3d` | 1.1.0 |
| `sample.neutral_vertical` | 1.0.0 |

运行入口会设置 `GM_MODULE_INDEX_PATH`。新游戏必须让 Profile、入口和环境变量指向同一索引；不能只改 preset feature 而仍加载另一套索引。

### 4.2 何时选 2D-only

适用于纯二维地图/角色呈现，或希望最小化发布面时。其导出必须排除：

- `gm_runtime/map/3d`
- `gm_adapters/spatial3d`
- `gm_runtime/content/3d`
- `gm_runtime/characters/visual_3d`
- `gm_runtime/presentation/planar3d`
- `gm_runtime/full_3d`
- 三维 combat/feedback 和三维 Manifest
- 三维交互 PlayerShell 脚本及 Planar3D 正式入口/合同

验收不能只检查模块列表；还要扫描实际包 inventory 和正式入口的递归依赖，确认三维根成员为零。

### 4.3 何时选 Planar3D-enabled

适用于逻辑仍是平面坐标，但需要 Node3D、三维角色视觉、三维呈现风格和场景执行的游戏。它允许声明过的 Planar3D 根，但仍明确排除 `gm_runtime/full_3d/*`。扩展三维功能时应先新增/升级 Manifest，再由 Profile 选择；不要在游戏脚本中绕过模块解析器直接拼出未声明依赖。

## 5. Profile、身份与 Schema

当前 GM 中性发布 Profile 为 `gm.profile.ext3d10.neutral_yard`，发布身份为 `gm.release.ext3d11.planar3d` / `1.0.0`。它绑定：

- enabled/disabled 入口；
- enabled/2D-only Manifest index；
- 地图、图、surface、scene definition、recipe、task 等稳定 ID；
- `user://gm_ext3d11_neutral_yard.world.json`；
- 视觉编译缓存 schema；
- Planar3D 性能预算资源。

关键持久化合同：

| 层 | Schema |
|---|---|
| world file | `gm.simulation_world.v6` |
| world snapshot | `gm.world_snapshot.v2` |
| Store snapshot | `gm.store_snapshot.v3` |
| Planar3D save record | `gm.planar3d.save_record.v1` |
| migration declaration | `gm.planar3d.save_migration.v1` |
| visual recipe | `gm.character.visual_recipe.v1` |
| visual compile cache | `gm.character.visual_compile_cache.v1` |

保存记录必需字段是 `entity_id`、`visual_recipe_id`、`map_id`、`spatial_domain`、`logical_position`、`surface_id`、`facing`、`world_state`。当前合同不承诺缺字段重建；缺任意必需字段要在 detached validation 阶段失败，并保证世界、Store、投影和 live Store 身份不变。新增 schema 或迁移器时，必须同时更新声明、实现、负向用例和最终 manifest。

## 6. 依赖预检与资源裁剪

### 6.1 依赖扫描器

`GMDependencyScanner.scan_project()` 扫描 `gm_runtime`、`gm_adapters` 和 `project.godot`。运行时默认禁止依赖：

- `res://addons/gm_editor`
- 源仓库内部开发样板路径（GitHub 清洁发布版不提供）
- 源仓库内部测试路径（GitHub 清洁发布版不提供）
- 源仓库内部运行证据路径（GitHub 清洁发布版不提供）
- 项目自定义文档排除路径

它不仅查字面量，还查 Resource/PackedScene 递归依赖、`load/preload` 静态表达式和运行时脚本中的 Editor API。无法静态确认的路径表达式会进入 `unresolved_expressions`，不能当作通过；应改成明确资源路径或在审查中给出边界证明。

建议在项目内保留一个只读审计 runner，核心调用如下：

```gdscript
extends SceneTree

func _initialize() -> void:
    var result := GMDependencyScanner.scan_project()
    print("GM_DEPENDENCY_SCAN " + JSON.stringify(result))
    quit(0 if result.ok and result.unresolved_expressions.is_empty() else 1)
```

上述 runner 是项目应自行实现、保存并审查的模板，不是 GitHub 清洁发布版自带命令；在项目真正创建该脚本前不得把示意路径放入流水线。

### 6.2 导出规划器

`GMExportPlanner.plan(profile, entry_scene)` 使用解析后的 Manifest ownership 生成 `allowed_paths`、`excluded_paths` 和 violations。规则要点：

- 编辑器、测试、报告和开发目录是绝对安全边界；
- selected module 的 required ownership 可覆盖普通模块间排除冲突，但不能覆盖绝对排除目录；
- 未获 Profile/Manifest 许可的 `res://` 依赖默认拒绝；
- 2D-only 对外公开的 plan 会移除 Planar3D 路径；
- `.godot/exported` 只允许由选定 Manifest 推导出的有限平台生成文件，不接受任意缓存文件。

不要以“文件没有被场景直接 preload”为理由跳过规划器；字符串 load、Resource 依赖和生成资源同样属于交付边界。

## 7. 构建与导出操作手册

### 7.1 通用环境准备

以下模板全部使用变量，不写死任何工作站路径：

```bat
@echo off
setlocal
set "GODOT_EXE=<本机 Godot 4.6.2 可执行文件>"
set "GM_PROJECT_ROOT=<本机游戏项目目录>"
set "BUILD_OUT=<本机构建输出目录>"
if not exist "%BUILD_OUT%" mkdir "%BUILD_OUT%"
```

先做导入/解析检查：

```bat
"%GODOT_EXE%" --headless --path "%GM_PROJECT_ROOT%" --import
if errorlevel 1 exit /b 1
```

成功标准不是仅 exit 0，还应确认日志无 `SCRIPT ERROR`、`Parse Error`、`Failed to load`、missing resource。Godot 退出期 `ObjectDB instances leaked` / `resources still in use` 在本轮被保留为 DN-02 非阻断诊断，但新出现、数量持续增长或运行期资源泄漏仍需调查。

### 7.2 生成 2D-only 候选

```bat
"%GODOT_EXE%" --headless --path "%GM_PROJECT_ROOT%" --export-debug "GM_P27_2D_Only_Debug" "%BUILD_OUT%\game_2d_debug.exe"
if errorlevel 1 exit /b 1

"%GODOT_EXE%" --headless --path "%GM_PROJECT_ROOT%" --export-release "GM_P27_2D_Only_Release" "%BUILD_OUT%\game_2d_release.exe"
if errorlevel 1 exit /b 1

"%GODOT_EXE%" --headless --path "%GM_PROJECT_ROOT%" --export-pack "GM_P27_2D_Only_Release" "%BUILD_OUT%\game_2d_release.pck"
if errorlevel 1 exit /b 1
```

对应 preset features 分别为 `gm_ext_3d_11_2d_only,p27_2d_only_debug` 和 `gm_ext_3d_11_2d_only,p27_2d_only_release`。正式入口必须仍是 `gm_ext_3d_11_2d_entry.tscn`。

### 7.3 生成 Planar3D-enabled 候选

```bat
"%GODOT_EXE%" --headless --path "%GM_PROJECT_ROOT%" --export-debug "GM_P27_Planar3D_Enabled_Debug" "%BUILD_OUT%\game_planar3d_debug.exe"
if errorlevel 1 exit /b 1

"%GODOT_EXE%" --headless --path "%GM_PROJECT_ROOT%" --export-release "GM_P27_Planar3D_Enabled_Release" "%BUILD_OUT%\game_planar3d_release.exe"
if errorlevel 1 exit /b 1

"%GODOT_EXE%" --headless --path "%GM_PROJECT_ROOT%" --export-pack "GM_P27_Planar3D_Enabled_Release" "%BUILD_OUT%\game_planar3d_release.pck"
if errorlevel 1 exit /b 1
```

对应 features 为 `gm_ext_3d_11,p27_planar3d_enabled_debug/release`，正式入口必须是 `gm_ext_3d_11_entry.tscn`。

### 7.4 Debug、Release 与 PCK 的含义

- Debug EXE 用于诊断构建配置和开发期回归。
- Release EXE 是面向交付的优化候选。
- PCK 用于独立核对资源裁剪、递归依赖和入口语义；它不是可以跳过 EXE 验证的替代品。
- 当前四个 P27 EXE preset 都设置 `binary_format/embed_pck=true`。即使 EXE 内嵌包，仍应额外导出 PCK 做可审查 inventory。
- 所有候选必须来自同一源码快照，禁止分别从不同工作区状态拼装。

## 8. 正式入口和合同测试

### 8.1 Planar3D 入口参数

`gm_ext_3d_11_release.gd` 支持：

- `--gm-ext-3d-11-contract`：执行 13 项发布合同；
- `--gm-ext-3d-11-save`：通过正式 PlayerShell/SimulationWorld/GMStore 保存；
- `--gm-ext-3d-11-restore`：独立进程恢复；
- `--gm-ext-3d-11-atomic-negative`：破坏必需字段并验证原子拒绝；
- `--gm-ext-3d-11-list-pack`：实际包 inventory 和递归依赖检查；
- `--gm-ext-3d-11-evidence=<path>` 或环境变量 `GM_EXT_3D_11_RUN_EVIDENCE`：写 JSON 证据。

EXE 合同模板：

```bat
set "RUN_EVIDENCE=%BUILD_OUT%\planar3d_contract.json"
set "GM_EXT_3D_11_RUN_EVIDENCE=%RUN_EVIDENCE%"
"%BUILD_OUT%\game_planar3d_release.exe" --headless --gm-ext-3d-11-contract
if errorlevel 1 exit /b 1
```

PCK 合同模板：

```bat
"%GODOT_EXE%" --headless --path "%GM_PROJECT_ROOT%" --main-pack "%BUILD_OUT%\game_planar3d_release.pck" -- --gm-ext-3d-11-contract
if errorlevel 1 exit /b 1
```

13 项应覆盖：样板 ready、Profile、enabled freeze、enabled export plan、2D crop、save/schema/atomic recovery、视觉缓存重建、10/30/60 性能预算、禁区扫描、缺依赖/Profile 负向、CAW gate 保持下游、真实 PlayerShell 保存重开、真实 release record 校验。

### 8.2 2D-only 入口

2D-only 正式合同的封存结果是 9/9。使用同名 2D 参数和入口脚本输出的 `GM_EXT_3D_11_2D_RESULT` 作为判据；至少要包含模块三项精确匹配、导出规划无三维泄漏、保存合同、实际包 inventory 和禁区扫描。不要把旧版 8/8 证据当作当前最终 9/9 基线。

### 8.3 跨进程保存/恢复

保存与恢复必须是两个真正独立的进程；同进程 resource reload 不算跨进程证据。

```bat
set "RUN_USER_ROOT=%BUILD_OUT%\userdata_planar3d"
if not exist "%RUN_USER_ROOT%" mkdir "%RUN_USER_ROOT%"
set "APPDATA=%RUN_USER_ROOT%\AppData"
set "LOCALAPPDATA=%RUN_USER_ROOT%\LocalAppData"

"%BUILD_OUT%\game_planar3d_release.exe" --headless --gm-ext-3d-11-save
if errorlevel 1 exit /b 1

"%BUILD_OUT%\game_planar3d_release.exe" --headless --gm-ext-3d-11-restore
if errorlevel 1 exit /b 1
```

隔离 `APPDATA/LOCALAPPDATA` 是测试夹具做法，目的是避免开发机历史存档污染。正式游戏则应通过独立 `config/name`、独立 Profile save path 和独立项目身份获得自己的 Godot `user://`。

还必须验证：

- 无存档首启正常；
- 合法存档可由新进程恢复；
- 坏 world schema、坏 Store schema、缺必需字段均拒绝；
- 失败前后世界、Store、投影及 live authority 不变；
- 不存在第二保存根或旧路径 fallback。

## 9. GUT 与分层测试策略

源仓库内部曾使用 GUT 9.6.1、测试目录和专用 runner 做开发验收；这些依赖、路径和命令不随 GitHub 清洁发布版提供。接收方应在自己的游戏仓库选择、安装并验证测试框架，不应在本发布树照抄内部命令。

大型仓库不建议每次只跑全量。提交前按影响面分层：

1. 单元测试：数据对象、验证器、Store、模块解析；源仓库内部 GUT 不随本清洁版提供；
2. 合同场景：项目自建合同场景或 runner（源仓库内部测试路径不随本清洁版提供）；
3. 正式入口：源工程启动，不用测试入口代替；
4. 导出候选：Debug、Release、PCK；
5. 跨进程：保存进程退出，再启动全新恢复进程；
6. 负向：缺资源、错误 schema、非法 Profile、错误显式目标；
7. 通用性：至少一个非默认 Profile/namespace，证明代码不是只对中性样板硬编码通过。

测试 runner 必须保留原始失败结果；修正夹具后追加新的结果，不得覆写失败历史。测试成功也不能替代包内 inventory 或独立 GUI 验收。

## 10. 包清单、摘要与候选对应

正式包检查应遍历完整 `res://`（跳过缓存、版本控制、编辑器插件，以及项目明确排除的测试、证据、文档和开发样板根），并同时检查入口递归依赖。Planar3D required paths 至少包括正式入口、release Profile、budget Profile、三维角色运行时和视觉预算管理器。

机器 manifest 至少记录：

- seal/baseline；
- 源码不可变快照或归档及单一 SHA-256；
- 每个候选的相对路径、大小、SHA-256、magic（EXE=`MZ`，PCK=`GDPC`）；
- 模块选择、入口、preset、合同通过数；
- GM/Godot/模块/schema 版本；
- 依赖和许可证分类；
- 禁止路径、保留风险、回滚输入；
- 是否已复制、是否已签发、谁负责独立复审。

推荐校验模板：

```bat
certutil -hashfile "%BUILD_OUT%\game_planar3d_release.exe" SHA256
certutil -hashfile "%BUILD_OUT%\game_planar3d_release.pck" SHA256
```

摘要只能证明字节身份，不能证明功能。必须同时保留正式启动、合同、inventory、跨进程恢复和源码/候选对应证据。

## 11. 性能预算

当前 `gm_ext_3d_11_budget_profile.tres` 的冻结值：

- near/far：12 / 32；hysteresis：1；
- 最大可见动画角色：30；
- 最大 full-quality 角色：10；
- 最大 skinned meshes：60；
- animation update budget：20；
- feature module budget：20；
- mid/far sampling：12 Hz / 8 Hz；
- animation budget：4 ms；
- frame warning：33.4 ms；
- world viewport：640×360。

发布合同会实际创建 10、30、60 个角色，经过视觉解析器和预算管理器运行多个 frame，并检查 60 角色时发生 deferred update。封存测得 60 行最终 animation cost 约 0.046 ms、未触发 frame warning，但这是合同环境数据，不是目标游戏最终性能保证。

游戏增加模型复杂度、材质、动画图、灯光或视口分辨率后，必须建立自己的预算 Profile 和代表性场景重测。不要静默提高阈值来“修复”预算失败。

## 12. 独立游戏（CAW 类）复制流程

### 12.1 复制资格

复制前必须先有：

- 最终产品 seal；
- 同 baseline 的候选；
- 不可变源码归档或 Git commit；
- 归档 SHA-256；
- 最终复制 manifest；
- 独立复制资格复审和主审签发。

本轮实例使用确定性 USTAR tar，并证明解包文件数、总字节、listing、摘要和禁止路径均匹配。开发者不应从正在继续变化的 GM 工作区直接复制文件，也不能把 AP3 reviewer 输出、测试、报告、缓存或历史 handoff 混入游戏工程。

### 12.2 目标目录安全

目标必须：

- 位于 GM 工作区/仓库之外；
- 是用户明确授权的绝对根或其新子目录；
- 创建前不存在，或有精确的非覆盖升级方案；
- 不等于一个已有资产管线父目录；
- 不移动、覆盖、删除父目录任何既有内容。

若目标非空且路线未明确，立即停止并请求目标子目录和 Project ID。不要猜路径。

### 12.3 独立身份必须真实绑定到运行时

仅新增一份 identity JSON 不够。独立项目必须让正式入口实际加载新的 Profile，并形成完整边界：

- project ID：`caw.*` 或该项目自己的稳定命名空间；
- active Profile ID：独立值，不是 GM 中性样板；
- map/graph/surface/actor/entity/world ID：属于项目 namespace；
- 独立 `config/name`，从而获得独立 Godot user-data 目录；
- 独立 `user://...world.json`；
- 独立 Store/cache namespace；
- 不共享 GM 可写 Store、缓存或 editor temp；
- 运行时无原 GM 工作区绝对路径；
- GM frozen core 作为锁定依赖，不由下游项目直接修改。

本轮已验收实例最初就因“identity 文件存在但正式入口仍加载默认 GM Profile”被判 DB。修复后通过 CAW-owned 入口扩展点注入项目 Profile。这是后续项目复制最容易漏掉的一步。

### 12.4 复制后验收

至少检查：

- 目标只来自签名归档，未混入活动 GM 工作区；
- 禁止目录/文件为零；
- 正式入口实际启动；
- 选择的模块集合精确匹配；
- Profile binding 在运行证据中显示项目 Profile；
- 合同全通过；
- 包 inventory 与递归依赖无禁区；
- 保存进程和独立恢复进程都使用项目 save path；
- 错误目标和坏存档 fail closed；
- 默认 GM Profile/存档未被写；
- 父目录既有资产不变；
- 独立审查者复验后再签 acceptance seal。

## 13. 扩展和发布注意事项

新增功能时优先按以下顺序落位：

1. 明确唯一权威服务/资源，避免第二 Store、第二任务状态或第二空间坐标权威；
2. 新建或升级模块 Manifest，声明 runtime root、service specs、required/excluded paths；
3. 在 Manifest index 中显式选择，不依赖偶然 preload；
4. 让 Profile 绑定稳定 ID、入口、存档、schema 和预算；
5. 让导出 preset 与 Profile/Index 使用同一模式；
6. 添加正向、负向、跨进程和非默认 Profile 测试；
7. 导出 Debug/Release/PCK 并做 actual-pack inventory；
8. 更新最终 machine manifest，再走独立审查。

通用修复应先回到 GM 中性样板，经审查发布新版本，再由具体游戏升级锁定依赖。题材内容、命名角色、正式地图、美术资源、UI、shader、发布配置和游戏专属 `caw.*` 身份不应反向进入 GM 平台源码。

## 14. 故障排查

| 现象 | 优先检查 | 不应采用的“修复” |
|---|---|---|
| 导出成功但启动失败 | preset 的 `application/run/main_scene`、Profile、Manifest index、递归依赖 | 改用测试场景冒充正式入口 |
| 2D 包出现 3D 文件 | 2D preset exclude、Manifest ownership、动态 load、实际 pack inventory | 只看 selected modules 就宣布裁剪成功 |
| 新进程不恢复 | `config/name`、Profile save path、PlayerShell→SimulationWorld→GMStore 链、是否真为新进程 | 同进程 reload 代替跨进程测试 |
| 坏存档破坏现场 | detached validation、atomic coordinator、失败前后 world/Store/projection/identity | 捕获错误后继续部分提交 |
| 非默认 Profile 出现样板 ID | 生成 ID 是否从目标 Profile namespace 推导、编辑路径是否写死 | 为每个游戏维护第二张硬编码映射表 |
| identity 文件正确但运行仍是 GM Profile | 正式入口的 Profile 注入时机和运行证据 | 只检查配置文件存在 |
| GUT 通过但正式包失败 | 正式入口、preset include/exclude、PCK inventory、export feature | 把单元测试通过当作发布通过 |
| `ObjectDB/resources still in use` | 是否仅退出期、数量是否稳定、是否伴随运行异常 | 一律忽略所有泄漏告警 |
| CUA 截图 `0x80004002` | Windows build 与 `GraphicsCaptureSession.IsBorderRequired` API contract | 反复重启 Godot、换盘或伪造 GUI 证据 |

## 15. 已知风险和未覆盖范围

当前封存为 `P27_SEALED_GENERALIZED_WITH_AP3_RISKS`，独立 Planar3D 复制为 `CAW_PLANAR3D_COPY_ACCEPTED_WITH_DISCLOSED_RISKS`。以下仍未消除：

- `DN-01`：附加记录的外/内 surface 不一致可能仍被接受，尚未证明实际玩法影响；
- `DN-02`：Godot 退出期 ObjectDB/resources-in-use 诊断；
- `TN-01`：审查夹具/运行编排曾修正，原失败证据保留；

- `HX1_RETIRED_PLATFORM_INCOMPATIBLE`，明确不是 PASS；
- 8 组真人 GUI 验收仍开放：入口/首用理解，视觉层级/裁切/缩放与 B-VIS-01，键鼠/焦点/手柄/拖放，2D/3D 目标/相机/HUD 连续性，Definition/中文错误/UndoRedo，完整编辑器真人保存重开/引用修复/批量恢复，玩家纵向流程可感知反馈，误操作/取消/重试恢复。

HX1 失败根因是当时 Windows build 19044 不支持 helper 无条件调用的 `GraphicsCaptureSession.IsBorderRequired`，返回 `E_NOINTERFACE (0x80004002)`。这不是 GM 产品缺陷，也不能因此把 GUI 验收写成通过。未来若 CUA helper 提供 Windows 10 fallback、换到支持的系统，或安排真人验收，可复用积压清单补验。

## 16. 发布验收清单

### 构建前

- [ ] 明确选择 `2D-only` 或 `Planar3D-enabled`，没有隐式模块并集。
- [ ] Godot 版本是当前支持基线，或已经完成独立兼容审查。
- [ ] Profile、入口、Manifest index 和 preset 指向同一模式。
- [ ] 模块依赖可解析，版本和许可证已记录。
- [ ] dependency scan 无 violations、无未解释 unresolved expressions。
- [ ] 项目自建测试和影响面合同测试通过。

### 候选生成

- [ ] 从同一不可变源码状态生成 Debug、Release、PCK。
- [ ] 导出日志无 parse/missing/failed-to-load。
- [ ] 正式入口启动，未使用测试入口替代。
- [ ] 2D-only 实际包中三维根为零；Planar3D 中 Full3D 为零。
- [ ] package inventory、入口递归依赖和 required paths 全通过。
- [ ] EXE/PCK 大小、SHA-256、magic 已进入 manifest。

### 运行与持久化

- [ ] 模块合同为当前基线的 13/13 或 9/9。
- [ ] 无存档首启通过。
- [ ] 保存进程退出 0，独立新进程恢复退出 0。
- [ ] 坏 schema/缺字段原子拒绝且 authority 不变。
- [ ] 只有一个保存根；无旧路径 fallback。
- [ ] 非默认 Profile/namespace 生命周期通过。
- [ ] 性能预算在代表性场景通过，阈值未被静默放宽。

### 独立项目复制

- [ ] 已签发复制资格，输入绑定不可变归档/commit。
- [ ] 目标路径和 Project ID 由用户明确，目标创建不覆盖既有内容。
- [ ] active runtime Profile 确为项目 Profile，不是 GM 默认 Profile。
- [ ] 项目 user-data/save/Store/cache/editor temp 独立。
- [ ] 无原 GM 绝对路径、无共享可写权威。
- [ ] 未复制 tests、reports、review/evidence、handoff、`.godot`、日志、缓存、秘密或旧存档。
- [ ] 独立审查者已复验，风险披露随交付保留。

## 17. 给游戏开发者的最短落地路径

如果要基于 GM 搭建一款新游戏：

1. 先选 2D-only 或 Planar3D-enabled；
2. 在 GM 仓库之外创建全新工程目录和稳定项目 namespace；
3. 从已批准不可变版本复制平台源，而不是从活动工作区散拷；
4. 在项目自己的 `res://<project>/` 下创建 Profile、入口绑定、地图/图/surface/actor/entity 身份和 shell 配置；
5. 锁定 GM release/Manifest/schema，不直接改 frozen core；
6. 先跑依赖扫描和项目自建测试，再跑正式入口合同；
7. 导出 Debug、Release、PCK；
8. 做 actual-pack、跨进程存档、错误输入、非默认 Profile 和性能预算验收；
9. 建立最终 machine manifest 和回滚输入；
10. 完成真人 GUI 验收后再作最终游戏发布结论。

这条路径能最大程度复用 GM 的权威数据、模块裁剪、保存恢复和发布合同，同时避免把中性样板身份、开发插件、测试资产或平台工作区路径带进具体游戏。

## GitHub 清洁发布版边界

本文件保留平台功能、架构与研究价值；涉及历史测试环境的内容不代表本发布树可直接执行。GitHub 清洁发布版的 CLI 以当前 `gm_cli.gd` 帮助为准，只提供 `help`、`environment`、`compatibility`、`validate`、`modules` 五个只读命令。源仓库内部的测试、插件冒烟、导出冒烟、模块专项验收、GUT、测试目录、fixture、runner 与审查证据均不随本清洁版提供；接收方应在自己的游戏仓库建立测试与发布流水线。
