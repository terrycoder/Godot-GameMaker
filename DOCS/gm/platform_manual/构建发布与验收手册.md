# GM 构建、发布与验收手册

## 1. 发布原则

一个可交付候选必须同时绑定：不可变源码、模块选择、Profile/Manifest/入口、Debug/Release/PCK、正式运行合同、实际包清单、跨进程恢复、机器 manifest 和风险披露。单独的“Godot 导出成功”不是发布通过。

当前正式验证：Godot `4.6.2.stable.official.71f334935`。4.7.2 未验证。

## 2. 模块选择和 preset

| 模式 | 项目 Modules | 项目入口/preset | 仓库中的样板证据 |
|---|---|---|---|
| 2D-only | core, spatial.core, spatial.planar_2d | `studio_game/runtime/game_entry_2d.tscn`；`StudioGame_2D_Debug/Release` | EXT11 2D entry、P27 preset、9/9 仅是冻结样板 |
| Planar3D-enabled | 上述 + spatial.planar_3d, character.visual_3d, scene.execution, presentation.render_style_3d, sample.neutral_vertical | `studio_game/runtime/game_entry_planar3d.tscn`；`StudioGame_Planar3D_Debug/Release` | EXT11 3D entry、P27 preset、13/13 仅是冻结样板 |

P27/EXT11 preset 名、custom feature、CLI flag、sentinel、13/13 与 9/9 都是样板/封存合同，不能作为下游稳定接口。下游须建立项目自己的 preset、runner、sentinel 与检查总数；若复用 EXT11 适配层，先复制到项目目录并以合同测试冻结。2D preset 必须排除三维 map/adapter/content/character/presentation/combat/feedback/Manifest/入口；Planar3D 只允许已声明三维根并排除 `gm_runtime/full_3d`。

每个项目 preset 至少审查 `name`、`platform`、`runnable`、`export_filter`、include/exclude、`custom_features`、输出路径以及实际 main scene。构建前断言：`project.godot` main scene、ProjectProfile modules、ReleaseProfile Index/entry、preset feature 全部属于活动项目，日志不得出现 `gm.profile.ext3d*`、`gm.world.p25*` 或 CAW 身份。

## 3. 构建环境与预检

```bat
@echo off
setlocal
set "GODOT_EXE=<absolute path to Godot 4.6.2 executable>"
set "PROJECT_ROOT=<absolute project directory>"
set "BUILD_OUT=<absolute candidate output directory>"
if not exist "%BUILD_OUT%" mkdir "%BUILD_OUT%"

"%GODOT_EXE%" --headless --path "%PROJECT_ROOT%" --import
if errorlevel 1 exit /b 1
```

检查日志无 `SCRIPT ERROR`、`Parse Error`、`Failed to load` 和 missing resource。退出期 ObjectDB/resources-in-use 是当前保留诊断 DN-02；若发生在运行中、数量增长或伴随失败，仍需阻断调查。

GitHub 清洁发布版包含可移植 launcher：`gm_cli_launcher.py` 优先读取 `%GODOT_EXE%`，未设置时从 `PATH` 查找 `godot` 或 `godot4`，并固定使用脚本所在目录。发布版 CLI 只提供五个只读命令：

```cmd
gm_cli.cmd help
gm_cli.cmd environment
gm_cli.cmd compatibility
gm_cli.cmd validate
gm_cli.cmd modules
```

自动化也可直接调用 `gm_cli.gd`，并显式检查 exit code：

```cmd
"%GODOT_EXE%" --headless --path "%PROJECT_ROOT%" --script "%PROJECT_ROOT%\gm_cli.gd" -- environment
if errorlevel 1 exit /b %errorlevel%
```

dependency scan 必须覆盖 runtime、adapters、project settings、Resource/PackedScene 递归依赖、静态 load/preload 和 Editor API。`unresolved_expressions` 需要解释或修正，不能按零 violation 自动忽略。

## 4. 内部验收与合同测试边界

源仓库内部使用 GUT、测试目录和专用 runner 做分层验收；这些依赖及命令不随 GitHub 清洁发布版提供，不能在本发布树直接执行。研究方法仍是：单元测试 → 领域合同场景 → 正式源入口 → 导出候选 → 跨进程 → 负向 → 非默认 Profile 通用性。发布版使用者应在自己的游戏仓库建立相应测试依赖、目录和 runner。

## 6. 正式入口验证

仓库当前没有 `--studio-game-*` runner，以下是项目必须实现并冻结的接口合同，不是可执行命令：

| runner 操作 | 必须执行 | 成功输出/退出 |
|---|---|---|
| contract | 冷启动正式入口；读取 Runtime 后 active Profile/world/save、Registry committed index/modules、entry 和模式 | 项目唯一 schema/sentinel，所有 checks 逐项 true，exit 0 |
| save | 通过唯一 World/Shell 保存根写入已知状态并退出 | 记录 save path/schema/digest，exit 0 |
| restore | 在第二个 OS 进程恢复并核对已知状态 | 记录恢复值与身份，exit 0 |
| atomic-negative | 对有效存档副本分别破坏 world/Store/schema/必需字段，比较前后 live state | 拒绝码稳定且 world/Store/projection/object identity 不变，exit 0 |
| list-pack | 从实际 PCK 枚举排序后的成员和递归入口依赖 | required 全有、forbidden 为零，exit 0 |

接口伪代码：`parse project-owned operation → call actual save/restore/contract/inventory API → write machine JSON → print unique sentinel → quit(0/1)`。在 runner 实现、测试并绑定候选之前，不得把任何示意参数放进自动化命令。

在当前仓库中，`--gm-ext-3d-11-*`、`GM_EXT_3D_11_*_RESULT`、13/13 与 9/9 只用于回归 EXT11/P27 样板；P25 的 `--p25-*` 同样是 Shell 样板探针。EXT11 的 `incremental_gate_stays_downstream` 仅证明 EXT11 没有自行签发 CAW，不证明下游项目已通过独立复制审查。不得以测试入口替代项目正式入口，也不得只读 JSON `ok` 而忽略 exit code、检查明细和原始日志。

## 7. Actual-package 验收

包清单必须同时验证：

- entry 真正 started；
- required paths 全存在；
- 完整包路径中 formal forbidden hits=0；
- entry 的 `ResourceLoader.get_dependencies()` 递归闭包无 missing/forbidden；
- 2D 三维根成员=0；
- Planar3D Full3D 和 fixture/旧入口=0；
- addons/tests/reports/docs/dev_samples 不进入正式包。

P27 样板 EXE 使用 embedded PCK；下游仍要独立导出 PCK 做 inventory。项目必须先实现上表的 `list-pack` 操作，或采用锁定 Godot 版本且经审查的 pack listing 工具，再以 allow/deny 清单比较。源工程目录文件数不能代替包内文件数。

## 8. 跨进程存档与原子拒绝

2D 与 Planar3D 使用同一验收编排规范：为该模式创建空隔离 user-data；进程 A 执行项目 runner 的 save 操作并退出；确认进程完全结束；进程 B 在同一隔离 user-data 执行 restore；随后由新的负向进程对存档副本逐类损坏并调用 atomic-negative。这里故意不用不存在的命令行 flag；项目 runner 实现后，发布流水线才把其真实参数填入命令模板。

每个 save 与 restore 命令必须是两个先后启动并各自退出的 OS 进程。`atomic-negative` 应先复制有效存档到测试文件，再分别破坏 outer world schema、一个 Store schema 和必需字段；从坏文件恢复后比较 world/Store/projection/live Store identity 的测试前后快照。不可直接破坏唯一有效存档，也不可用同进程 reload 冒充跨进程。

必须分别证明：无存档首启；保存进程正常退出；第二独立进程恢复；坏 world/Store/schema/必需字段拒绝；失败前后 world、Store、projection、live Store identity 不变；仅有一个 save root；无旧路径 fallback。

当前 schema 是 world file `gm.simulation_world.v6`、snapshot `gm.world_snapshot.v2`、Store `gm.store_snapshot.v3`。当前不承诺全历史迁移或缺字段重建。

## 9. CAW/独立游戏复制隔离

### 9.1 资格输入

- 平台所有者/发布者签发的发布描述符、产品 seal 和同 baseline 候选；
- 同一描述符绑定的 archive、commit、大小、SHA-256、签名/信任根与逐文件 manifest；
- 允许根、ownership、签发者、撤销状态和最终机器复制 manifest；开发者不能自行宣称批准。
- 显式模块二选一；
- 独立资格复审与主审签发。

若最终 manifest 与历史 freeze manifest 冲突，只在明确 supersede 的复制门字段采用新 manifest；历史产品记录不删除、不追改。

### 9.2 安全复制

目标必须在 GM workspace/repository 外，由用户提供明确目录和 Project ID。目标非空、等于已有父目录或规则不明确时停止。不得覆盖、移动或删除同级美术/资产管线内容。

本仓库当前没有可向下游承诺的通用安全解包脚本；安全复制是发布门，不是单条 shell 命令。经审查工具须分阶段完成：验签及 hash/大小 → 只读 inventory → 拒绝绝对路径、盘符、`..`、反斜杠混淆、符号/硬链接及越界 link target、重复/大小写冲突、异常文件类型、允许根外成员和禁止内容 → 解包到新空暂存目录 → 逐文件 path/size/hash 对照 → 按 ownership 导入。目标已有美术管线内容时不覆盖同名文件；冲突立即停止。候选只作验证/回滚参考。

发布描述符还必须标明 bundle type。已验收 CAW 是 runtime copy，编辑器插件保持禁用；要使用 Dock，平台发布者必须另发 editor SDK 及其完整 addon/probe 依赖 manifest。两类包都不得把 editor/test 内容带入正式候选。

### 9.3 运行隔离

独立项目必须有：

- 项目稳定 namespace；
- active runtime Profile ID；
- 项目 map/graph/surface/actor/entity/world ID；
- 独立 `config/name` 与 Godot user-data；
- 独立 `user://` save path；
- 独立 Store/cache/editor temp；
- 零原 GM 工作区绝对路径；
- frozen GM core 只读依赖。

必须在正式运行证据中读取到项目 Profile。仅写一份 identity JSON 而入口仍加载默认 GM Profile，是交付阻断。

### 9.4 复制验收

执行者不能自审。独立审查至少重跑正式启动、模块合同、actual pack、保存/独立恢复、错误目标/坏存档、默认 GM Profile 未被写、父目录未变和路径扫描；最终由主审签 acceptance seal。

## 10. 性能预算

中性冻结预算：near/far 12/32、hysteresis 1、可见动画 30、full quality 10、SkinnedMesh 60、`animation_update_budget=20` 是每帧动画更新数；`feature_module_budget=20` 是分配给 Near 角色的 Feature 模块总数，不是每帧更新数；动画预算4ms、frame warning 33.4ms、world viewport 640×360。

合同用真实视觉对象测 10/30/60，并要求超量时出现 deferred update。具体游戏改模型、动画、材质、光照、视口后必须复制自己的 BudgetProfile，使用代表性场景重测。禁止静默提高阈值掩盖失败。

## 11. 候选 manifest

机器 manifest 至少包含：

- seal、baseline 和源 archive/commit；
- source SHA-256、文件数/字节数/解包规则；
- 每个 EXE/PCK 的相对路径、大小、SHA-256、magic；
- module selection、entry、preset、contract checks；
- GM/Godot/module/schema 版本；
- 依赖/许可证分类；
- forbidden paths、isolation contract、rollback input；
- copy/sign/review 状态；
- retained risks。

```bat
certutil -hashfile "%BUILD_OUT%\studio_game_2d_release.exe" SHA256
certutil -hashfile "%BUILD_OUT%\studio_game_2d_release.pck" SHA256
certutil -hashfile "%BUILD_OUT%\studio_game_planar3d_release.exe" SHA256
certutil -hashfile "%BUILD_OUT%\studio_game_planar3d_release.pck" SHA256
```

摘要证明字节身份，不证明功能；不能替代启动、合同、inventory 和恢复。

## 12. 故障定位

| 现象 | 检查 |
|---|---|
| 导出成功、启动失败 | preset entry、Profile/Index、递归依赖、feature |
| 2D 包含 3D | exclude filter、Manifest ownership、动态 load、actual inventory |
| 新进程不恢复 | `config/name`、active Profile/save path、PlayerShell→World→Store、是否真新进程 |
| 坏存档改了现场 | detached validation、atomic coordinator、contributor commit 是否会失败 |
| 非默认 Profile 出现样板 ID | ID 是否从目标 namespace 派生、路径是否写死 |
| identity 对但 runtime Profile 错 | 入口注入时机、实际 profile binding 证据 |
| 源仓库内部测试绿、包失败 | 正式入口、include/exclude、PCK inventory；该测试能力不随本清洁版提供 |
| CUA `0x80004002` | Windows/API contract；不要伪造 GUI 通过 |

## GitHub 清洁发布版边界

本文件保留平台功能、架构与研究价值；涉及历史测试环境的内容不代表本发布树可直接执行。GitHub 清洁发布版的 CLI 以当前 `gm_cli.gd` 帮助为准，只提供 `help`、`environment`、`compatibility`、`validate`、`modules` 五个只读命令。源仓库内部的测试、插件冒烟、导出冒烟、模块专项验收、GUT、测试目录、fixture、runner 与审查证据均不随本清洁版提供；接收方应在自己的游戏仓库建立测试与发布流水线。
