# GM 平台独立开发者可用性审查

## 1. 审查结论

**结论：REWORK_REQUIRED**

六份正式文档已形成完整的知识地图，能解释模块边界、编辑器工具、内容资源、运行时、保存恢复和发布验收体系；但当前版本还不能让一名未参与项目的 Godot 开发者仅凭文档稳定地从零搭建并验收一个独立游戏。

阻塞点不是“缺少功能说明”，而是若干关键步骤仍停留在概念或样板引用层：CLI 启动路径不可移植、独立项目交付物与安装步骤不明确、Project Profile/Manifest/正式入口缺少完整可复制样板、2D 发布验收命令不完整。直接照抄现有命令，存在命令无法启动、测试目录不匹配，或实际运行仍落入样板/默认 Profile 的风险。

本审查只检查文档及其所指向的源码、资源和报告；未修改六份正式文档，也未把尚未完成的 GUI 人工验收判为已通过。

## 2. 审查范围与模拟路径

按第一次接触本项目的 Godot 开发者的阅读顺序检查：

1. `说明文档总览.md`：选择 2D 或 Planar3D，并找到后续入口。
2. `游戏开发者快速入门.md`：从空项目建立平台依赖、项目身份、Profile、Manifest 和正式入口。
3. `GM平台技术手册.md`：配置地图、角色、NPC、任务、交互、Facility、Process、能力和事件，并理解编辑器、保存及运行时边界。
4. `构建发布与验收手册.md`：执行测试、CLI、导出、独立运行、保存恢复和负向验收。
5. `源码与扩展点地图.md`：在扩展或排错时定位公共 API、内部实现、样板资产和证据。
6. `文档构建与校验报告.md`：核对文档声明、未验收项和当前基线。

静态核查还覆盖了文档实际引用的 `gm_cli.cmd`、`gm_cli_launcher.py`、`gm_cli.gd`、`GMProjectProfile`、`GMPlayerShellConfiguration` 以及 2D/Planar3D 验收脚本入口。

## 4. 必须修正的问题

### R1 — CLI 启动器与文档变量约定矛盾（阻塞）

涉及 `构建发布与验收手册.md` 的“变量约定”“CLI 基线验证”，`游戏开发者快速入门.md` 的环境检查，以及 `文档构建与校验报告.md` 关于命令可替换的结论。

本节保留的是初版审查时发现并已关闭的问题：当时 launcher 与文档变量约定不一致。当前 GitHub 清洁发布版的 `gm_cli_launcher.py` 已优先读取 `%GODOT_EXE%`，未设置时从 `PATH` 查找 Godot，并以发布树根作为工作目录。

```text
<本机 Godot 4.6.2 控制台程序>
```

上述行为仅描述初版问题，不再描述当前发布版；关闭证据见本报告后续复审章节。

可执行修正建议：

1. 已修正：启动器读取 `%GODOT_EXE%`，并在无法解析 Godot 时给出明确错误。
2. 文档入口改为 `call "%PROJECT_ROOT%\gm_cli.cmd" ...`，或直接给出可移植形式：

   ```bat
   "%GODOT_EXE%" --headless --path "%PROJECT_ROOT%" --script "%PROJECT_ROOT%\gm_cli.gd" -- environment
   ```

3. 每组命令加入 `if errorlevel 1 exit /b %errorlevel%`，避免失败后继续生成貌似成功的证据。
4. `文档构建与校验报告.md` 在此修正验证完成前，不应继续宣称所有命令均已安全变量化。

### R2 — “从空独立项目开始”缺少平台交付物取得与安装步骤（阻塞）

涉及 `游戏开发者快速入门.md` 的前置条件、Stage A/B，以及 `构建发布与验收手册.md` 的 CAW/独立工程基线。

现文档要求使用“批准的不可变归档或提交”，但未给出交付包从哪里取得、怎样校验、怎样解包、应该出现哪些根目录，也没有说明独立项目是复制整个平台根、只复制 addon，还是依赖外部平台路径。持有六份文档但未参与交付的人无法完成第一步。

可执行修正建议：增加“平台交付包”前置表和一套可替换命令，至少包含：

- `GM_PLATFORM_ARCHIVE` 或仓库/提交的明确占位符；
- 预期 SHA-256 或 manifest 文件；
- 解包到 `%PROJECT_ROOT%` 的命令；
- 必须存在的最小目录/文件清单，例如 `project.godot`、`addons/gamemaker_next`、运行时与 CLI 文件；
- 解包后检查命令和预期输出；
- 平台目录与游戏内容目录的所有权边界，明确美术/内容管线目录不会被覆盖。

### R3 — Project Profile、Manifest、Registry 与正式入口没有形成可复制闭环（阻塞）

涉及 `游戏开发者快速入门.md` 的 Stage C、D、G，以及主手册的 Profile/Manifest/Registry、PlayerShell、正式入口章节。

当前示例主要是 GDScript 属性赋值片段或字段清单。它没有给出一套完整且可直接保存的 `.tres` 文件头、脚本 `ext_resource`、资源路径、正式 `game_entry.gd/.tscn`，也没有完整展示：加载项目 Index/Profile → `GMModuleRegistry.resolve()`/显式校验 → 安装 `GMRuntimeContext` → 构建 PlayerShell → 将主场景写入 `project.godot` 的顺序。

这会让开发者“创建了身份文件”，但运行时仍可能载入默认或样板 Profile。文档也提到 CAW 曾出现身份 JSON 存在、活动运行时仍使用默认 GM Profile 的问题，因此这里必须是硬性可验证步骤。

可执行修正建议：新增一个完整的最小项目骨架，所有文件均可复制后运行：

- `res://studio_game/config/project_profile.tres`
- `res://studio_game/config/module_index.tres`
- `res://studio_game/config/player_shell.tres`
- `res://studio_game/runtime/game_entry.gd`
- `res://studio_game/runtime/game_entry.tscn`
- `project.godot` 中 `[application] run/main_scene` 的设置

示例必须给出 Project ID/Profile ID/World ID/Save Path 的断言日志，并在启动时验证活动 Profile 与预期项目身份一致；校验失败应非零退出，而不是回退到样板。

### R4 — “Profile”术语混用，职责边界与真实字段不一致（高）

涉及 README 对 Profile 职责的概述、Quickstart 全文的 Profile/样板 Profile/Release Profile，以及主手册相关章节。

真实 `GMProjectProfile` 仅包含：

```text
template_id
enabled_modules
spatial_domain_id
spatial_backend_id
spatial_backend_enabled
```

稳定内容身份、地图/角色引用、相机、存档路径等主要由 `GMPlayerShellConfiguration` 持有；Planar3D 发布预算和发布入口又属于发布 Profile。当前文档将“模块、空间域、入口、稳定身份、保存和预算”统称为 Profile 职责，容易让读者把字段填到错误资源中。

可执行修正建议：加入统一术语表，至少区分：

- `GMProjectProfile`：模块选择与空间域/后端；
- `GMPlayerShellConfiguration`：世界、地图、玩家、内容引用、相机和保存路径；
- 中立竖切样板 Profile：示例内容编排，不是新游戏身份；
- Planar3D Release Profile：发布入口、预算和发布验收配置。

后文所有裸写的“Profile”应替换为具体类型名；若只是概念集合，应明确写“配置组合”。

### R5 — 2D 构建、保存恢复和负向验证没有可执行对称流程（阻塞）

涉及 `构建发布与验收手册.md` 的 2D 验收、保存恢复、独立导出运行，以及 Quickstart Stage H。

Planar3D 给出了 contract、save、restore、atomic-negative、list-pack 等具体参数；2D 只概述使用正式入口与 `GM_EXT_3D_11_2D_RESULT`，并引用当前 `9/9` 结果。选择 2D 的开发者没有等价的两进程保存/恢复、损坏存档负向、实际 pack 和证据目录命令。

源码中的 2D 验收入口已经暴露 `--gm-ext-3d-11-formal-product`、`--gm-ext-3d-11-2d-contract`、`--gm-ext-3d-11-2d-only-check`、`--gm-ext-3d-11-list-pack`、`--p25-save-exit`、`--p25-contract` 等参数，但正式构建文档没有把它们组织成可执行闭环。

可执行修正建议：增加与 Planar3D 同结构的“2D 正式产品验收”章节，逐条给出：

1. 2D-only 模块/依赖校验；
2. 正式入口 contract；
3. 第一进程写存档并退出；
4. 第二个独立进程正常恢复；
5. 损坏存档原子失败和恢复策略；
6. 实际 PCK 内容检查；
7. 预期退出码、结果标识和证据文件。

不得仅以仓库当前 `9/9` 结果替代新项目自己的验收。

### R6 — 测试目录约定互相冲突（高）

初版 Quickstart 与构建文档曾使用不一致的内部测试目录。相关 GUT 命令和源仓库测试路径均不随 GitHub 清洁发布版提供；新游戏必须在自己的仓库定义测试根。

可执行修正建议：定义统一变量，例如：

修正原则是由项目明确自己的测试根；若平台测试与游戏测试都必须执行，应在项目自己的测试流水线给出各自通过标准及不可排除的套件。

### R7 — 导出 preset 仍以样板名说明，缺少“不会导出错入口”的核验（高）

涉及构建文档的 ExportPreset 创建与导出命令，以及 Quickstart 发布步骤。

文档要求复制 `GM_P27_*` preset 结构再改名，但未列出哪些字段必须修改、哪些字段必须保留；示例命令仍使用 P27 preset 名。开发者可能成功生成 EXE/PCK，却仍携带样板主场景或样板 Profile。

可执行修正建议：提供项目化 preset 对照表和完整最小例子，至少覆盖 preset 名、目标平台、输出路径、include/exclude filter、自定义 feature、`application/run/main_scene`、正式 Profile/配置资源、debug/release 差异。导出后必须通过日志或 contract 断言活动 Project/Profile/World ID 与新项目一致。

## 5. 应补强但不阻塞理解的问题

### U1 — 内容资源的“新建方式”和依赖顺序应统一列出

主手册已列出大量真实字段，但第一次搭建竖切的开发者仍需在 Dock、Inspector 和复制样板三种路径间自行推断。建议增加按依赖排序的最小内容表，每项注明：从哪个 Dock 创建；若无专用 Dock，明确写“在 Inspector 中新建 Resource”；推荐路径和资源类型；必填/可空字段；被谁引用以及怎样进入 PlayerShell 或正式入口；一个不依赖样板专有 ID 的最小例子。

推荐顺序：Map/Surface → Character/Role → NPC → Interaction/Object → Task → Facility/WorkSpot → Process → Ability → Event Trigger → PlayerShell → 正式入口。

### U2 — Facility、WorkSpot、Process 的编辑入口应明确边界

文档容易让读者以为每类内容均有专用 Dock。现有材料主要展示其 Resource、Inspector 字段和样板 Profile 编排。应直接说明哪些能力有专用 Dock，哪些必须通过 Inspector 或样板资源创建，以免开发者寻找不存在的 Facility/Process 编辑器。

### U3 — 样板替换清单应升级为启动前硬性门禁

建议形成可勾选清单，并把样板 Project/Profile/World/Map/Character/NPC/Task/Facility/Process/Ability/Event ID、样板保存路径、P27 preset 名及中立竖切资源路径纳入启动 contract。任何残留应报错或至少产生显著警告。

### U4 — 命令运行位置与参数分隔应明确

所有批处理命令应声明当前目录，或全部使用完整路径。对于 `project.pck` 与独立 EXE，应分别给出已经测试的用户参数分隔写法，并说明哪些脚本读取 `OS.get_cmdline_user_args()`，避免开发者凭经验增删 `--` 后得到不同结果。

## 7. 复审通过条件

完成以下验证后可改为 PASS：

1. 在没有仓库历史背景、Godot 安装路径不同的新环境中，仅按文档取得并解包平台交付物。
2. 只使用文档提供的文件和命令，分别创建一个 2D 项目和一个 Planar3D 项目。
3. 两个项目启动日志均证明加载的是项目自己的 Project Profile、Manifest、PlayerShell 配置和正式主场景，而不是样板或默认 Profile。
4. CLI、导入、导出命令及项目自建测试均可从文档声明目录执行，变量替换后不依赖作者机器路径；源仓库内部 GUT 不随本清洁版提供。
5. 2D 与 Planar3D 均完成独立导出运行、实际 pack 检查、两进程保存/恢复和损坏存档负向验证。
6. GUI 人工项继续单列，不得因自动化通过而改写为 PASS；完成后记录 Godot 版本、操作证据和复现步骤。

在上述条件完成前，六份文档适合用作架构和功能参考，但不应宣称已经是“未参与项目的开发者可独立照章搭建并发布”的完整操作手册。

### 8.3 残留阻塞问题

#### RR-01 — Quickstart 的项目入口适配代码会被父类重新绑回 EXT11 样板

涉及：`游戏开发者快速入门.md` 第 9 节入口脚本模板；关闭表 R3。

Quickstart 的 Planar3D 示例在调用 `super._ready()` 前执行：

```gdscript
OS.set_environment("GM_MODULE_INDEX_PATH", RELEASE_PROFILE.module_manifest_index)
sample_profile = RELEASE_PROFILE
```

但实际父类 `gm_runtime/vertical_sample/gm_ext_3d_11_release.gd` 的 `_ready()` 会立即：

1. 把 `GM_MODULE_INDEX_PATH` 覆写为固定的 `res://gm_runtime/manifests/gm_ext_3d_11_manifest_index.tres`；
2. 因 Quickstart 没有给 `release_profile` 赋值，从固定 `RELEASE_PROFILE_PATH` 加载 `gm_ext_3d_11_profile.tres`；
3. 再把 `sample_profile` 覆写成该 EXT11 样板 Profile。

因此示例的项目 ReleaseProfile 和项目 Manifest Index 在真正运行前被撤销，随后 active-identity 检查只会失败退出；它不能构成关闭表声称的“可复制闭环”。

2D 同样受阻：`gm_ext_3d_11_2d_only.gd::_ready()` 无条件把 `GM_MODULE_INDEX_PATH` 覆写为固定 EXT11 2D Index。Quickstart 虽要求调用父类前设置项目 `two_d_manifest_index`，但父类随后会把它改回样板路径。2D 能保留调用者预设的 `sample_profile`，却不能保留项目 Manifest Index。

可执行修正建议：

- 不要把这两个带硬编码 `_ready()` 的脚本直接当项目基类；文档应给出真实“复制到项目目录并修改后的 adapter”完整代码，或先由产品提供可注入的正式入口基类。
- 若继续继承 Planar3D 样板，至少必须在 `super._ready()` 前设置父类实际读取的 `release_profile = RELEASE_PROFILE`，并改造父类使 Index 只在未配置时 fallback；仅设置 `sample_profile` 不够。
- 2D 父类也必须允许显式 Index 覆盖，并在 Registry 首次读取前保持项目路径。
- 修正文档后，用一个非 `ext3d/p25/caw` ID 的真实临时项目执行启动，保存原始日志，证明 Registry 解析的是项目 Index，active Profile/World/Save 均为项目值；静态出现代码片段不能作为关闭证据。

#### RR-02 — 从最小 `project.godot` 启动后，文档要求使用的编辑器 Dock 不会自动出现

涉及：Quickstart 第 4 节、第 6–8 节和“最小 `project.godot` 闭环”；关闭表 R3/U1/U2。

Quickstart 要求新开发者依次使用“GM地图工作台”“GM语义地图”“GM平面3D地图”“GM 三维场景配方策划”“GM角色资产库”“GM角色NPC装配”“GM任务工作台”等 Dock，但全文没有启用编辑器插件的步骤。给出的最小 `project.godot` 也没有 `[editor_plugins]` 配置。平台主 Dock 来自 `res://addons/gm_editor/plugin.cfg`；Planner 等功能还可能需要各自插件。仅把 `addons/` 解包到项目中不会启用插件，因此新项目打开后无法执行后续 Dock 步骤。

可执行修正建议：

- 在阶段 A 加入明确操作：Godot `项目 > 项目设置 > 插件` 中启用哪些插件，并列出每个模式的最小插件集合及出现的 Dock 名称；或在完整 `project.godot` 示例中加入经 Godot 保存的 `[editor_plugins] enabled=PackedStringArray(...)`。
- 区分运行时必需、仅编辑期、仅测试期插件；不要让可选第三方插件意外进入正式包。
- 增加启用后的验收点：Dock 列表、一次新建/Undo/Redo/保存/重开，不把程序化 Dock 实例化当成人工通过。

#### RR-03 — 不可变归档只给校验/解包模板，仍缺“取得批准输入”的可执行交接

涉及：Quickstart 第 2.3、阶段 A；构建手册 9.1/9.2；关闭表 R2。

返工已补充 SHA-256、inventory、禁止项、ownership 和解包检查，这是显著进步。但开发者仍只看到：

```bat
set "GM_PLATFORM_ARCHIVE=<absolute immutable platform archive path>"
set "GM_PLATFORM_SHA256=<approved-lowercase-sha256>"
```

六份正式文档没有定义批准归档的交付位置/命名规则、谁签发 expected hash/seal、签名文件/公钥如何取得，或本版最小交付 manifest 的具体名称。文档说“发布系统应另提供签名验证”，但没有可跟随的交接接口。独立开发者无法仅凭文档判断手中归档和 hash 是否属于同一批准发布。

此外，示例只把 `tar -tf` 输出交给一条 `findstr` 过滤后直接解包，没有明确拒绝符号链接/硬链接、Windows 盘符和反斜杠 traversal 等归档成员。它应标成说明性模板，而不是安全解包的完整实现。

可执行修正建议：

- 定义一个正式“平台发布描述符/交接单”，包含 archive 文件名、版本、commit、大小、SHA-256、签名算法、签名文件、公钥/信任根、文件 manifest 名称及签发角色；Quickstart 只需引用稳定取得位置或随包路径。
- 把当前命令明确标为完整性预检示例；安全解包应调用经过测试的仓库脚本/工具，检查绝对路径、盘符、`..`、反斜杠、link target、重复/大小写冲突和目标 ownership，再执行 extraction。
- 复审使用一个真实批准归档完成“取得 → 验签/hash → inventory → 解包 → manifest 复核”，记录命令与预期输出。

### 8.4 非阻塞但需修正的准确性问题

- `文档构建与校验报告.md` 把 R3 标为“已关闭”，但其“示例静态检查”同时说明没有执行生成型示例；鉴于 RR-01 是父类运行时覆写，静态存在 preflight/identity 字样不能证明闭环。关闭表应改为重新打开，直到真实临时项目跑通。
- 构建手册定义 `--studio-game-*` runner 约定，并在保留限制中承认它不是现成 API。Quickstart 应把“实现 runner”列为阶段内的显式开发任务，给出最小接口和每个命令的退出条件；否则命令是规范，不是复制即用验证。
- Quickstart 的 `project_identity.json` 只列出应记录的字段，没有完整 JSON 示例或运行时消费者；既然正文明确说该文件本身不算绑定，建议将其定位为发布元数据，并指向实际读取/核对它的 runner 或 manifest 工具。

### 8.5 再次复审的通过条件

1. 修正后的 2D 与 Planar3D 入口不再由父类覆盖项目 Manifest/Profile，且真实冷启动日志证明项目身份生效。
2. 从文档给出的最小项目壳打开 Godot 后，开发者能按明确步骤启用所需插件并看到对应 Dock。
3. 平台发布描述符使归档、hash、签名、manifest 与签发者形成可核对的同一交付；安全解包不依赖不完整的单条 `findstr`。
4. `文档构建与校验报告.md` 的关闭表引用一次真实从零运行证据，而不只引用静态片段存在性。

在这四项完成前，复审结论保持 **REWORK_REQUIRED**。

## 9. 第二轮返工最终复审（2026-09-08）

### 9.1 最终结论

**DOCUMENTATION_USABILITY_FINAL_PASS**

本轮仅复核上一轮残留项。正式文档已不再把未实现能力包装成可复制入口或可执行命令；新开发者可以明确区分“已经验收的 CAW-owned Planar3D 冻结 EXT11 适配”与“必须由项目另行实现、测试和取证的通用能力”。因此上一轮 RR-01、RR-02、RR-03 的文档可用性阻塞均已关闭。
