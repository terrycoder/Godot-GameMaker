# GM 平台正式文档技术准确性审查

## 1. 结论

**REWORK_REQUIRED**

六份正式文档已经正确描述了大部分平台边界，尤其是 Profile/Manifest/Registry 的组合关系、SimulationWorld 单一保存根、原子恢复、2D/Planar3D 区分、视觉 Recipe/Cache 权威边界、Godot 版本基线及 HX1 非 PASS 状态。但当前仍有会让新游戏项目按文档直接接入失败或错误依赖样板实现的问题，因此在修正前不能判为 PASS。

本审查只读抽查实际源码、正式合同和封存报告，没有修改六份被审文档或产品代码。

## 3. 必须修正的问题

### TA-01（高）：Quickstart 的命名规则会生成无法通过现有领域校验的 ID

受影响位置：

- `GM平台技术手册.md` 第 4.2 节，第 93 行：“不要占用平台 `gm.*` 身份”。
- `游戏开发者快速入门.md` 第 2 节与第 6.1 节，尤其第 170–171 行的 `studio.game.actor.player`、`studio.game.entity.player`。

源码事实：

- `gm_runtime/simulation/gm_entity_id.gd:4,24` 明确要求实体身份以 `gm.entity.` 开头；`GMEntityRegistry.register_entity()` 位于 `gm_runtime/simulation/gm_entity_registry.gd:12`，会走该校验。
- `gm_runtime/vertical_sample/gm_neutral_vertical_sample_profile.gd` 的角色校验还要求 actor 以 `gm.actor.`、entity 以 `gm.entity.` 开头。
- `gm_runtime/process/gm_process_definition.gd:25,122-123` 的 `definition_id` 只接受 `gm.*` 或历史 `p20.*`。
- Task signal/provider 也有类型前缀约束，例如 `gm_runtime/tasks/gm_task_definition.gd:50,129` 要求 `gm.<signal_kind>.*` / `gm.fact.*`。

影响：照 Quickstart 建出的 entity（以及照“完全避开 gm.*”理解后建立的 Process/Fact 等）会在注册或 Resource 校验时被关闭式拒绝。这不是风格问题，而是教程不可执行。

修正建议：把“项目命名空间”和“类型前缀”拆成两层。项目不得复制 `gm.ext3d*`、P25/P27 或 CAW 的既有身份，但必须服从每种 schema 的前缀合同。例如实体可写成 `gm.entity.studio_game.player`，角色写成 `gm.actor.studio_game.player`，Process 写成 `gm.process.studio_game.craft`，Fact 写成 `gm.fact.studio_game.crafted`；允许自由命名的 project/profile/map 等再使用项目拥有的命名空间。为 Quickstart 中每一类示例 ID 标明对应 validator，而不是给出一条全局“不要使用 gm.*”。

### TA-02（高）：PlayerShell 被标成通用稳定组合 API，但当前实现仍是 P25/纵向样板绑定

受影响位置：

- `源码与扩展点地图.md` 第 3 节将 `gm_player_shell.gd` 标为 “Public composition API”。
- `GM平台技术手册.md` 第 3.2、4.2、11.1 节把 PlayerShell/正式入口作为一般项目组合边界。
- `游戏开发者快速入门.md` 第 9 节要求项目入口“注入项目 Profile，再调用既有启动链”，但未给出受支持的基类、字段和调用方式。

源码事实：

- `gm_runtime/player_shell/gm_player_shell.gd:15-17` 固定 P25 Store/schema/2D manifest；第 21–31 行固定 `gm.p25.*` 输入动作；文件后半还包含 P25 contract/save/restore/2D-only probe 和固定输出 sentinel。
- `gm_runtime/player_shell/gm_player_shell_configuration.gd:9-10,147-167` 只从固定 `res://gm_runtime/player_shell/configurations/` 目录按命令行 ID 装载配置，并回退默认样板配置。
- 当前可验证的 Profile 注入模式实际来自样板继承链：`gm_ext_3d_11_release.gd:1-20` → `GMNeutralVerticalSample` → `GMPlayerShell`；EXT11 先设置样板 release profile/manifest，再 `super._ready()`。这不是一个与样板无关的 `GMProjectProfile` 通用入口合同。

影响：开发者会把 P25 输入、Store ID、HUD 和测试参数带入自己的产品，或尝试一个文档未定义且没有独立公共合同测试的“基类初始化前注入”。这正是把样板能力冒充稳定 API 的风险。

修正建议：

1. 将 `GMPlayerShellConfiguration` 标为“当前可配置 schema/样板扩展缝”，将 `GMPlayerShell` 标为“P25 正式样板组合实现（可冻结复制，不是模块中立 ABI）”，除非平台先完成去 P25 化并新增公共合同。
2. Quickstart 必须二选一：给出经过验证的、完整的项目入口子类模板（明确继承类、export 字段、Profile 类型、manifest 设置、`super._ready()` 顺序），或要求复制已签名 CAW/EXT11 模板并替换所有样板身份。不要只写“调用既有启动链”。
3. 明确哪些 `handle_action()`、保存 contributor、输入 action 和 CLI probe 是样板内部实现，不能作为下游稳定 API。

### TA-03（高）：发布手册把 EXT11/P27 样板 preset 与命令写成了项目通用命令

受影响位置：

- `构建发布与验收手册.md` 第 2、5、6、8、13 节：直接使用 `GM_P27_*` presets、`gm_ext_3d_11` 入口、`--gm-ext-3d-11-*` 参数和 13/13、9/9 计数。
- `游戏开发者快速入门.md` 第 10 节要求独立项目建立自己的 preset/入口，却没有定义项目合同 runner 如何替代上述样板参数。

源码事实：

- 参数只由 `gm_runtime/vertical_sample/gm_ext_3d_11_release.gd:11,23-32,299,312-313` 和 `gm_ext_3d_11_2d_only.gd:42,50-52,183,197-198` 解析。
- `GM_EXT_3D_11_*` sentinel、13 项检查及 package inventory 都是上述样板入口生成；普通项目入口不会天然响应这些参数。
- 13 项中的 `incremental_gate_stays_downstream` 在 `gm_ext_3d_11_release.gd:106-107` 验证的是 `eligible_for_copy_ready == false`；`gm_planar3d_release_contract.gd:432` 明确 EXT11 自身不签发 downstream copy-ready。

影响：独立项目若已正确替换入口或 preset，照文档执行会得到未知参数、没有 sentinel，或者错误地沿用 GM 样板候选名称与合同计数。文档还可能让人把“downstream gate 保持未签发”的检查误读为 CAW gate 已通过。

修正建议：把现有命令单独标为“GM P27/EXT11 参考候选的冻结验收”，并新增“下游项目必须实现/冻结的等价合同”小节：项目自己的 preset、入口、参数或 runner、sentinel/schema、检查清单和基线计数。将 13 项中的 CAW 描述改为“确认增量合同不越权签发 downstream gate”；CAW 是否通过只能引用最终 copy/acceptance seal。

### TA-04（中）：Ability 与 Transaction 被写成无条件同一条链

受影响位置：

- `说明文档总览.md` 第 19 行：“玩家、AI、日程与事件统一进入 Ability/Transaction 事务链”。
- `GM平台技术手册.md` 第 6.2 节的 `submit_operation() → Ability/Transaction → Store/Fact` 若被理解为全 Ability 通用顺序，也会过度概括。

源码事实：

- `gm_runtime/gas/gm_ability_definition.gd:106-125` 只有 `fact_type` 非空时调用 `execute_domain_transaction()`；否则可调用 `executor_service_id` 对应的 `execute_domain_command()`，甚至以 `ability.completed_without_domain` 完成。
- `gm_runtime/gas/gm_ability_system_host.gd:453` 是事务路径，`925` 是非事务 domain-command 路径。
- `gm_runtime/movement/gm_movement_ability_executor.gd` 提供自己的 request 生命周期；它不能被概括成每次都产生 Fact/Change 的事务提交。

影响：扩展者可能错误要求纯表现/移动/无领域 Ability 必须创建 Resolver 和 Fact，或反过来绕过真正需要事务的写入。

修正建议：改为“所有来源统一形成 AbilityActivationRequest；需要权威领域写入且声明 `fact_type` 的 Ability 才进入 Resolver/Transaction→Fact/Change/Cue；executor-only 与 no-domain Ability 走各自明确分支”。Task Service 的具体 `submit_operation()` 事务链可以保留为领域实例，不应上升为所有 Ability 的唯一流程。

### TA-05（中）：视觉 feature budget 被错误描述为“每帧 Feature 更新 20”

受影响位置：

- `GM平台技术手册.md` 第 12.2 节，第 391 行。
- `构建发布与验收手册.md` 第 10 节，第 179 行。

源码事实：

- `gm_runtime/characters/visual_3d/gm_character_visual_budget_profile.gd:14` 定义 `feature_module_budget = 20`，而 animation update 是另一个字段。
- `gm_runtime/presentation/planar3d/gm_visual_budget_manager_3d.gd:81` 用该值判断 Near 角色的累计 `feature_module_count` 是否还能装配，不是按帧调度 20 次 feature 更新。

影响：开发者会用错误指标做性能验收和预算调参。

修正建议：写成“每帧动画采样/更新预算 20；Near 角色可分配的 feature module 总预算 20”，并分别说明超限行为。保留 10/30/60 场景合同，但不要把两个不同量纲合并成“各 20 次更新”。

### TA-06（中）：Source Map 列出了不存在的 Content Library `resolve` 方法

受影响位置：`源码与扩展点地图.md` 第 5 节，Content Library 行写作 `scan/query/resolve`。

源码事实：`gm_runtime/content/gm_content_library.gd` 的公共方法为 `scan()`（第 16 行）、`reload()`（136）、`query()`（139）、`entry_for_id()`（152）、`entry_for_path()`（157）、`inspect_thumbnail()`（160）、`set_usage_status()`（175）、`snapshot()`（181）；没有 `resolve()`。

影响：这是明确的类/方法名错误，开发者按 Source Map 查找会失败。

修正建议：改成实际方法名，例如 `scan/reload/query/entry_for_id/entry_for_path`。若“resolve”只是概念说明，不应使用方法式写法。

### TA-07（低）：CLI 示例没有建立 `gm_cli.cmd` 的可执行路径

受影响位置：

- `构建发布与验收手册.md` 第 3 节，第 36–42 行。
- `GM平台技术手册.md` 第 15 节，第 476–482 行。

问题：发布手册设置了 `%PROJECT_ROOT%`，但未 `pushd` 到仓库根，也未调用 `%PROJECT_ROOT%\gm_cli.cmd`。从任意工作目录复制代码块时命令不可执行；独立游戏项目如果没有复制工具文件也会失败。

修正建议：明确前置条件“当前目录为含 `gm_cli.cmd` 的 GM/项目根”，或使用 `call "%PROJECT_ROOT%\gm_cli.cmd" ...`。同时说明独立项目是否应携带 CLI 工具，还是从冻结 SDK 工具目录调用。

### TA-08（低）：手册混用了 EXT10 内容 Profile 与 EXT11 发布 Profile，容易形成错误权威

受影响位置：`GM平台技术手册.md` 第 4.2 节，第 87 行只推荐 `gm_ext_3d_10_profile.tres`；发布和构建文档实际以 `gm_ext_3d_11_profile.tres` 为当前正式候选。

源码事实：`GMNeutralVerticalSample` 默认使用 EXT10 content profile；`GMExt3D11Release` 再加载 EXT11 release profile 并覆盖 `sample_profile`。两者角色不同，不能只称为一个泛化的“Planar3D 样板 Profile”。

修正建议：明确 EXT10 是中性纵向内容/Profile 基础，EXT11 是当前发布绑定 Profile（含 manifest、entry、budget/cache 合同）；新项目应复制哪一层取决于是否复用发布合同。

## 4. 抽查通过项

以下内容与当前源码/证据一致，本次未要求返工：

- **Profile/Manifest/Registry**：文档正确要求 Profile、Manifest Index、entry、preset 保持一致；`GMModuleRegistry.resolve()/validate_explicit()/manifest_contract()` 等方法和路径存在。
- **Registry 提交快照边界**：文档关于先构造候选、校验后提交、下游不覆盖 committed snapshot 的方向与 `gm_module_registry.gd` 当前实现一致。
- **保存与原子恢复**：`GMSimulationWorld.save_snapshot()/save_to_file()/load_snapshot()` 路径存在；`gm_atomic_world_load_coordinator.gd` 先建立 detached registry/event/stores，执行 contributor prepare，再做引用/值 swap。文档关于坏 schema/Store/必需字段拒绝且不应留下部分 live 状态的要求正确。
- **单一保存根与 contributor**：PlayerShell 将自身投影和 EXT11 增量写入 World 所拥有的 Store，并通过 atomic restore participant 准备/提交；文档没有把 cache 或 HUD 投影提升为第二权威。
- **2D/Planar3D**：逻辑 `GMPlanarPosition`、Surface Graph 与 3D 投影的边界描述准确，且明确未开放 Full3D；2D-only 三维裁剪要求与 manifest/export 合同一致。
- **Visual Recipe/cache**：Recipe 是内容权威，compile cache 可删可重建的描述准确。
- **版本**：`gm_platform_version.tres:8-10` 是 Godot `4.6.2.stable.official.71f334935` 基线，4.7.2 仅 compatibility target；六份文档没有把 4.7.2 写成已验证。
- **HX1/GUI**：六份文档均保持 `HX1_RETIRED_PLATFORM_INCOMPATIBLE` 为非 PASS，并明确程序化、non-headless 或 JSON 证据不能替代八组真人 GUI 验收。
- **路径/链接抽查**：六份正式文档的 Markdown 相对链接均指向现存同目录文件；Source Map 抽查的 runtime、editor、test、contract、seal 路径存在。未发现已检查范围内的死链接。
- **构建报告统计**：`文档构建与校验报告.md` 的行数采用“包含末尾空行”口径，与当前六份文件的显示行号/尾换行一致；不将空行过滤计数当成其口径。

## 5. 复审通过条件

完成 TA-01、TA-02、TA-03 三项高优先级修正后，至少用一个全新项目 namespace 做静态/轻量合同走查：

1. Quickstart 中 actor/entity/process/fact 示例全部通过对应 validator。
2. 项目入口的继承、Profile 注入、Manifest 设置、`super._ready()` 顺序可以由明确源码模板复现。
3. 项目自有入口不依赖 `--gm-ext-3d-11-*` 仍能完成启动、包 inventory、跨进程保存/恢复和负向原子拒绝，或文档明确要求冻结复制 EXT11 runner 并完成改名/再验收。
4. 修正 TA-04 至 TA-08 的术语和命令后，重新运行文档路径、围栏、方法名和示例命令校验。

## 6. 双审返工复审（2026-09-08）

### 复审结论

**REWORK_REQUIRED**

TA-04、TA-05、TA-06、TA-07、TA-08 的原始问题已按源码边界关闭；TA-01 的示例 ID 主体已修正，TA-02/TA-03 的“样板而非稳定 ABI”文字边界也已补齐。但新加入的入口、preset 与保存命令没有形成可执行闭环，`文档构建与校验报告.md` 第 2 节把 TA-02、TA-03、R3、R5、R7 标为“已关闭”目前没有技术依据。

### RR-01（阻断）：Planar3D 项目入口模板会被父类重新绑定回默认 EXT11 Profile/Manifest

受影响位置：`游戏开发者快速入门.md` 第 9 节约第 381–406 行。

模板在进入父类前执行：

```gdscript
OS.set_environment("GM_MODULE_INDEX_PATH", RELEASE_PROFILE.module_manifest_index)
sample_profile = RELEASE_PROFILE
shell_configuration = SHELL_CONFIGURATION.duplicate(true)
super._ready()
```

但实际父类 `gm_runtime/vertical_sample/gm_ext_3d_11_release.gd:14-20` 会：

1. 把 `GM_MODULE_INDEX_PATH` 无条件重设为 `res://gm_runtime/manifests/gm_ext_3d_11_manifest_index.tres`；
2. 因继承字段 `release_profile` 仍为 `null`，加载默认 `gm_ext_3d_11_profile.tres`；
3. 再用该默认值覆盖 `sample_profile`；
4. 随后的 `super._ready()` 又继续进入中性样板/P25 Shell。

因此文档模板的项目 ReleaseProfile 不会成为父类实际 active profile，项目 Manifest 环境入口也被改回样板。模板末尾的 active identity 检查虽然能 fail closed，但只能证明它必然失败，不能构成“可复制闭环”。单把赋值改成 `release_profile = RELEASE_PROFILE` 仍不能解决父类硬编码 Manifest；必须提供项目拥有并已审查的入口适配脚本（复制后替换硬编码），或先在产品代码中提供不回写默认值的受支持注入 hook，再按该 hook 写模板。

2D 分支同样不能只“换首行基类”：`gm_ext_3d_11_2d_only.gd:12-20` 会无条件写回默认 2D Manifest，`GMPlayerShell._ready():171-173` 在 2D delivery 下还会写 P25 2D Manifest。必须逐层说明/消除这些样板重绑定点，并在进入 Runtime 构建后断言 Registry committed view 的 `index_path` 与 selected modules，而非只在父类调用前做预检。

### RR-02（阻断）：文档执行的 `--studio-game-*` 合同/保存命令没有 runner 实现

受影响位置：

- `构建发布与验收手册.md` 第 6–8 节约第 127–184 行；
- `游戏开发者快速入门.md` 的入口模板。

构建手册执行 `--studio-game-contract/save/restore/atomic-negative/list-pack`，但 Quickstart 给出的 `game_entry.gd` 只处理 `_ready()` 和打印一次 boot identity；没有解析这些参数，也没有调用 save、restore、atomic-negative 或 pack inventory，更没有打印 `STUDIO_GAME_*_RESULT` 后退出。其父类只识别 `--gm-ext-3d-11-*`（`gm_ext_3d_11_release.gd:11,23-32,312-313`）或 P25 probe。因此照抄命令时，程序会进入普通运行而不是执行合同并退出，`if errorlevel` 也无法验证文档声称的结果。

`文档构建与校验报告.md` 第 4 节虽然承认 `--studio-game-*` 是“下游应实现的 runner 约定”，但正式构建手册把它们放在可执行命令块，Quickstart 又称入口/场景为最小闭环。两者冲突。

修正要求：要么提供完整可解析的项目 runner 模板（每个参数的实际调用、唯一 sentinel、成功/失败 exit code、两个独立进程的 save/restore、坏存档副本和 atomic 对比）；要么把这些命令明确改为伪代码/验收接口规范，禁止表述为当前可复制执行命令，并说明开发者还必须实现 runner 后才能使用。

### RR-03（高）：新增 2D preset 片段不能实现文档声明的三维裁剪

受影响位置：`构建发布与验收手册.md` 第 5 节约第 99–123 行。

示例采用 `export_filter="all_resources"`，同时只排除 `gm_runtime/planar3d/**`、`gm_runtime/characters/visual_3d/**` 和 `gm_runtime/full_3d/**` 等少数路径。仓库实际 3D 根包括但不限于：

- `gm_runtime/map/3d/**`
- `gm_adapters/spatial3d/**`
