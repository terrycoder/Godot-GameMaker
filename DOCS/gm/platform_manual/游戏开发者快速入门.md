# GM 游戏开发者快速开始

## 1. 目标

本教程从一个空白的独立游戏工程出发，完成最小垂直切片：项目身份 → 模块 → Profile → 地图/角色/设施 → Task/Process/Ability → PlayerShell → 保存恢复 → 导出候选。

示例使用占位项目 ID `studio.game` 和 ID 命名空间段 `studio_game`。请在开始前替换；类型前缀必须在命名空间之前，例如 `gm.actor.studio_game.*`，不要写成 `gm.studio_game.actor.*`，也不要复制 EXT/P27/CAW 身份。

当前工具链只按 Godot `4.6.2-stable official` 验证。不要用 4.7.2 开始正式项目，除非另走兼容审查。

## 2. 先做三个选择

### 2.1 项目身份

定义并记录：

```text
project_id       = studio.game
profile_id       = studio.game.profile.vertical_slice
release_id       = studio.game.release.vertical_slice
map_id           = gm.map.studio_game.start
graph_id         = gm.graph.studio_game.start
save_path        = user://studio_game_vertical_slice.world.json
```

项目目录必须在 GM 仓库外，且是用户明确授权的新目录。项目 `config/name`、Profile、user-data、save path、Store/cache namespace 都要独立。

### 2.2 空间模式

| 选择 | 使用场景 | 模块 |
| 顺序 | 先创建 | 之后才能安全引用 |
|---|---|---|
| 2D-only | 纯二维地图/角色、最小发布面 | `core`、`spatial.core`、`spatial.planar_2d` |
| Planar3D-enabled | 二维逻辑 + Surface Graph + 三维表现 | 上述三项加五个 Planar3D 模块 |

不要先复制两套再“以后决定”；模式从 Manifest Index、Profile、入口到 export preset 必须一致。

### 2.3 平台版本

使用已批准的不可变 GM 源码归档或提交。记录其版本/摘要和来源 seal。不要从仍在修改的 GM 工作区挑文件复制。

## 3. 最小目录与资源清单

建议项目拥有自己的目录，不改 frozen `gm_runtime`：

```text
res://
  project.godot
  export_presets.cfg
  gm_runtime/                 # 锁定的平台依赖
  gm_adapters/                # 所选空间适配器
  addons/                     # 仅开发期所需插件
  studio_game/
    config/
      project_identity.json
      module_index.tres
      project_profile.tres
      player_shell.tres
    runtime/
      game_entry.gd
      game_entry.tscn
    content/
      characters/
      objects/
      abilities/
      tasks/
      processes/
      visual/
    maps/
      start_map.tres
      start_semantics.tres
      start_surface_graph.tres # 仅 Planar3D
    scenes/
      start_scene_recipe.tres  # 仅 Planar3D
    tests/
      test_vertical_slice.gd
```

最小资源：

- 项目 identity、Profile、Manifest Index、PlayerShell configuration；
- 一张地图和至少一个 entry Anchor/Surface；
- 玩家 Character，至少一个 NPC；
- 一个可交互 Object 或 Facility/WorkSpot；
- 一个 Ability/Event/Fact 链；
- 一个 TaskObjective；
- 一个可启动并完成的 Process；
- 项目入口；
- 独立 save path；
- Debug/Release preset。

按依赖顺序创建，避免 Dock/校验器在引用尚不存在时给出级联错误：

| 顺序 | 先创建 | 之后才能安全引用 |
|---|---|---|
| 1 | project identity、两类 Module Index、`GMProjectProfile` | Registry/空间预检 |
| 2 | map、surface、anchor、route/connection | actor、facility、scene recipe |
| 3 | content/character/visual resources | actor/entity 与对象定义 |
| 4 | facility/workspot/resource account、process definition | actor target、reservation、task |
| 5 | ability/interaction、fact/event type | task objective、event trigger |
| 6 | task/assignment、scene/session recipe | Shell/垂直流程 |
| 7 | ReleaseProfile、ShellConfiguration、项目入口 | 测试与导出 preset |

2. 只从批准的不可变归档解包平台文件。通用 `cmd.exe` 模板如下；归档的发布系统应另提供签名验证，SHA-256 只是完整性/身份核对：

## 4. 阶段 A：取得平台交付物并创建工程壳

1. 平台所有者/发布者交付同一批准批次的发布描述符；开发者不能自行把任意 archive/hash 宣称为“已批准”。描述符至少包含 bundle type（editor SDK 或 runtime copy）、archive 文件名、版本、commit、字节数、SHA-256、签名算法与签名文件、信任根/公钥标识、逐文件 manifest、允许根、签发角色、签发时间和撤销状态。
2. 由发布流水线或经审查的安全解包工具执行“取得 → 验签 → hash/大小 → inventory → 解包 → 解包后 manifest 对照”。本仓库当前没有可向下游承诺的通用安全解包脚本，因此这里是交付门，不提供一条 `findstr + tar` 命令冒充安全实现。
3. inventory 门必须拒绝：绝对路径、Windows 盘符、任意 `..` 段、反斜杠路径混淆、符号链接/硬链接及越界 link target、重复项、大小写冲突、未声明文件类型、超预算尺寸和允许根外成员。只解包到新建空暂存目录；完成逐文件 path/size/hash 对照后，再按 ownership 清单导入新项目子树。
4. 目标已有美术或内容管线时不得覆盖同名文件。平台交付默认拥有 `gm_runtime/`、所选 `gm_adapters/` 和经批准的 editor addon；游戏团队拥有 `studio_game/`。任何 ownership 冲突立即停止并交由发布者重新出包。
5. runtime copy 禁止包含 `tests`、`reports`、review/evidence/handoff、`.godot`、user data、日志、缓存、秘密或旧存档。editor SDK 可包含其 manifest 明确声明的编辑器 probe/fixture，但这些仍是开发期依赖，候选包必须排除。
6. 修改项目 `config/name`，创建发布元数据 `studio_game/config/project_identity.json`。该 JSON 本身不是运行时绑定；只有 bootstrap/候选 runner 对活动 Profile、Manifest、world/save 的运行后证据才算通过。
7. 只有发布者提供 editor SDK 且其依赖校验通过时，才在 Godot 的“项目 → 项目设置 → 插件”启用 `res://addons/gm_editor/plugin.cfg`；CAW 已验收的 runtime copy 明确禁用了插件，不能拿它完成 Dock 教程。`TileMapDual` 按需；`gm_agent_planner`、`gm_feedback`、`gm_p26_vertical_sample` 是专项/样板工具；`gut` 仅测试期。所有 addon 都不是正式候选运行时依赖。

启用后确认所需 Dock 出现，并人工完成一次新建 → Undo/Redo → 保存 → 关闭重开；程序化实例化 Dock 不代替这项人工检查。
5. 让正式入口实际加载项目 Profile；identity 文件存在本身不算绑定成功。

验收点 A：

- [ ] 目标目录没有覆盖父目录既有内容。
- [ ] 复制来源可追溯到不可变归档/commit。
- [ ] 运行时无原 GM 工作区绝对路径。
- [ ] 发布描述符、archive、签名、hash、manifest 来自同一批准批次。
- [ ] 暂存目录原为空，inventory 与解包后 manifest 精确一致。
- [ ] Godot 打开/导入无 parse 或 missing resource；所需 Dock 已出现。

## 5. 阶段 B：建立模块 Index 与 Profile

先区分四类同名概念：`GMProjectProfile` 只负责模块/空间；`GMPlayerShellConfiguration` 负责 world/map/player/camera/save；`GMNeutralVerticalSampleProfile` 是 EXT10 内容编排样板；`GMPlanar3DReleaseProfile` 是继承前者并增加 Manifest/entry/cache/budget 的 EXT11/P27 发布样板。当前能直接跑通的 Shell 路径仍受 P25/EXT11 绑定；下游必须拥有适配层并替换后两类样板中的全部身份，不能把它们误称为通用 ABI。

### 5.1 2D-only 分支

项目 Index（完整 `studio_game/config/module_index.tres`）：

```ini

  "res://gm_runtime/manifests/core.tres",
  "res://gm_runtime/manifests/spatial_core.tres",
  "res://gm_runtime/manifests/spatial_planar_2d.tres"
])
```

模块选择 Profile（完整 `studio_game/config/project_profile.tres`）：

```ini

[ext_resource type="Script" path="res://gm_runtime/gm_project_profile.gd" id="1"]

[resource]

spatial_backend_id = "gm.spatial.backend.planar_2d"
spatial_backend_enabled = true
```

入口不得引用任何三维运行根。

### 5.2 Planar3D-enabled 分支

Planar3D 另建 `module_index_planar3d.tres`，沿用上面的完整 Resource 外壳并加入：

```text
spatial_planar_3d.tres
character_visual_3d.tres
scene_execution.tres
render_style_planar_3d.tres
vertical_sample.tres   # 可先参考，成品应替换样板内容
```

选择八模块组合，并另建 `project_profile_planar3d.tres`，把 `enabled_modules` 改为八模块、`spatial_domain_id` 改为 `gm.spatial.planar_3d`、`spatial_backend_id` 改为 `gm.spatial.backend.planar_3d`。逻辑空间仍用 `GMPlanarPosition`；三维场景是 Surface Graph 投影。不要启用 Full3D reserved。

### 5.3 验证

项目自有 composition root 必须在 Registry 首次读取前设置项目 Index，再调用 `resolve()`、`validate_explicit()`、`manifest_contract()` 并安装 Context；运行后用 `GMModuleRegistry.current_view_result()` 断言 `index_path` 与 selected modules。当前 P25 Shell 会在内部创建 Context，EXT11/P25 父类还会重写 Index；因此这些 ProjectProfile/Index 文件不会仅因存在而自动生效。采用下文 CAW 冻结适配路径时，活动 Index 是锁定 EXT11 Index；要使用项目自有 Index，必须实现并测试不继承这些 `_ready()` 的项目 composition root。

验收点 B：

- [ ] selected modules 精确等于选择。
- [ ] required dependencies 闭合、无 conflict、无重复 service。
- [ ] Profile/Index/入口一致。
- [ ] 一个 Context 只有一个 active spatial backend。

## 7. 阶段 D：角色、NPC、对象和视觉

### 7.1 2D 角色

1. 创建外部唯一 Character Definition 和 VisualSet。
2. 导入帧/SpriteFrames；配置 idle/move/attack/hurt/death。
3. 配 one/four/eight/four_mirrored 方向、anchors 和 event frames。
4. 分别保存两个不同 `.tres`，重开验证 Definition 仍引用 VisualSet。
5. 在“GM角色NPC装配”绑定 RoleProfile、Shape2D、地图和出生 Anchor，保存 PackedScene。

### 7.2 Planar3D 视觉

1. 创建项目 `GMCharacterVisualRecipe`。
2. 用稳定 Content ID 绑定 Body/Head/Hair/Outfit/Feature/Accessory/Posture/Skeleton/Animation/Palette。
3. 校验 canonical bones、sockets、FitClass 和动作。
4. 编译/命中缓存；删除缓存后重建。
5. 用“GM角色3D装配”绑定项目 Actor ID。

### 7.3 对象

创建 Object Definition 和 InteractionRecipe；从内容库拖入地图；装配稳定实例 ID、Owner 和 Anchor。预览修复不写权威，只有“应用修复”提交。

验收点 D：

- [ ] 没有 `gm.ext3d*` 样板 actor/entity ID。
- [ ] Recipe 不保存 Node/RID/PackedScene。
- [ ] 缓存删除后可重建。
- [ ] Object 交互通过 Ability/Transaction 返回 committed result。

## 8. 阶段 E：Facility、Process、Task 与 Ability

### 8.1 Facility/WorkSpot

为 WorkSpot 声明 anchor、surface、logical position、capacity、reservation rule、process definition、resource/account 和初始/恢复余额。Actor 只能引用已声明 WorkSpot。

### 8.2 Process

创建 `GMProcessDefinition`：稳定 ID、revision、family、duration、capability、facility target、completion kind/payload、可选 Task/Duty。通过 `gm.ability.process.*` 请求启动，使用逻辑 units 推进。

### 8.3 Task

在“GM任务工作台”：

1. 创建 TaskDefinition v2 和 Objective；
2. Objective 指向 committed `fact/change/cue` 类型和目标值；
3. 保存并注册 Definition；
4. 发布 Task、建立 Assignment；
5. 配 DutyProvider/Reservation；
6. 让 Objective 消费权威提交信号。

### 8.4 Ability/Event

为玩家交互、AI 和 Process completion 创建同一类 `GMAbilityActivationRequest`。领域写入经 Resolver/Transaction；事件触发器只负责 condition/target routing。

验收点 E：

- [ ] UI/Planner/Process 不直接写 Task 或资源账户。
- [ ] 幂等键稳定，同键不同材料被拒绝。
- [ ] Fact/Change/Cue 因果链一致。
- [ ] 预留失败、commit 失败和 rollback 失败均有恢复测试。

### 9.1 当前已验证参考：CAW-owned Planar3D 冻结适配

已验收 CAW 实例锁定整套 EXT11 Manifest/runner，建立项目自己的 ReleaseProfile、Shell Resource 和入口脚本；入口在 `super._ready()` 前同时赋值父类实际读取的 `release_profile` 与 `sample_profile`。父类仍会强制选择冻结 EXT11 Index，这是该参考路径的有意依赖，不是项目 Index 注入。下面片段只适用于“发布者批准的冻结 EXT11 Index/合同”；替换身份后必须重跑同等级合同。

按 CAW 模式，`release_profile.tres` 应挂接项目自有脚本，该脚本 `extends GMPlanar3DReleaseProfile` 并在 `_init()` 中显式替换 profile/map/graph/surface、`actor_specs`、`facility_specs`、`surface_specs`、`connection_specs` 和 save path；仅创建基础 `.tres` 会继承 EXT10 默认数组。Shell Resource 与本节完整示例一致。不得把 locked GM release/profile ID 当 active project identity。

```gdscript
extends GMExt3D11Release

const PROJECT_RELEASE_PROFILE_PATH := "res://studio_game/config/release_profile.tres"
const EXPECTED_PROFILE_ID := "studio.game.profile.vertical_slice"

func _ready() -> void:
    var candidate := load(PROJECT_RELEASE_PROFILE_PATH) as GMPlanar3DReleaseProfile
    if candidate == null or candidate.profile_id != EXPECTED_PROFILE_ID or not candidate.validate().ok:
        push_error("Project Planar3D release profile binding failed.")
        get_tree().quit(1)
        return
    # 两项都必须赋值；只赋 sample_profile 会被父类默认 Profile 覆盖。
    release_profile = candidate
    sample_profile = candidate
    super._ready()

func _write_evidence(value: Dictionary) -> Dictionary:
    var registry_view := GMModuleRegistry.current_view_result()
    value["profile_binding"] = {
        "profile_id": sample_profile.profile_id if sample_profile != null else "",
        "profile_resource": PROJECT_RELEASE_PROFILE_PATH,
        "world_id": shell_configuration.world_id if shell_configuration != null else "",
        "save_path": sample_profile.save_path if sample_profile != null else "",
        "registry_index_path": registry_view.get("index_path", ""),
        "selected_modules": registry_view.get("manifests", {}).keys()
    }
    return super._write_evidence(value)
```

锁定版本的 `GMPlanar3DReleaseProfile` 公开的是 `validate()`；升级平台时须重新核对真实方法并更新合同，不得用动态兼容调用吞掉缺失方法。

`studio_game/runtime/game_entry_planar3d.tscn` 绑定三项项目资源：

```ini
[ext_resource type="Resource" path="res://studio_game/config/player_shell.tres" id="2"]
[ext_resource type="Resource" path="res://studio_game/config/release_profile.tres" id="3"]
[node name="StudioGamePlanar3DEntry" type="Node"]
script = ExtResource("1")
shell_configuration = ExtResource("2")
sample_profile = ExtResource("3")
```

editor SDK 项目的最小 `project.godot`；runtime-only copy 应保持插件数组为空：


运行后证据必须显示项目 Profile/world/map/graph/surface/save，且 Registry `index_path` 精确等于批准的冻结 EXT11 Index、selected modules 为八模块。若要真正使用项目 `module_index_planar3d.tres`，不得继承会重写 Index 的 EXT11 `_ready()`。

### 9.2 2D-only 与项目自有 Manifest

当前没有已验收的通用 2D bootstrap。`gm_ext_3d_11_2d_only.gd` 和 `GMPlayerShell._ready()` 都会重绑 EXT11/P25 2D Index，因此禁止“只换基类”或只赋 `sample_profile`。2D 项目以及任何需要项目自有 Manifest 的项目必须实现项目 composition root：在 Registry 首次读取前选择 Index，校验并提交 Registry/Context，装配配置和领域服务，不调用会重写 Index/Profile 的样板 `_ready()`；Runtime 构建后断言 committed `index_path`、selected modules、Profile/world/save。平台提供模块中立 PlayerShell SDK 前，本文不声称存在复制即运行的通用 2D 入口。

插件启用优先由 Godot UI 保存。上例只启用主编辑器插件；按需追加 `TileMapDual`、`gm_agent_planner`、`gm_feedback`、`gm_p26_vertical_sample`，测试期才启用 `gut`。正式导出排除 `addons/*`。

### 9.3 垂直流程验收

最小可玩流程建议：

```text
玩家出生
玩家出生
 -> 移动到 Facility Anchor
 -> 交互产生 Ability request
 -> 获得 Reservation
 -> 启动并推进 Process
 -> Transaction 提交资源变化和 Fact
 -> Objective 消费 Fact，Task 完成
 -> HUD 显示 Projection/Cue
 -> 保存退出
```

验收点 F：

- [ ] 运行证据显示 active Profile 是项目 Profile。
- [ ] 输入经项目适配层构造公共 request/command，没有 UI 直写；P25 `handle_action()` 只作样板参考。
- [ ] Task/Process/资源变化来自 committed package。
- [ ] 2D/3D 切换只改空间/表现投影。

## 10. 阶段 G：保存恢复

1. 无存档启动，确认正常创建世界。
1. 在隔离 user-data 下无存档冷启动。
2. 经正式 PlayerShell 保存并退出进程。
3. 启动第二个独立进程，读取同一项目 `user://`，确认玩家、Task、SceneSession、Object、Process/Store 恢复。
4. 复制存档并破坏 schema 或必需字段，确认拒绝。
4. 复制有效存档为负向夹具，分别破坏 world schema、Store schema 与必需字段并尝试恢复。
5. 比较失败前后 world/Store/projection/live identity 完全不变。

扩展状态必须注册 atomic contributor：prepare 只验证 detached candidate，commit 只做无失败交换。禁止第二 JSON 保存根。

验收点 G：

- [ ] world=`gm.simulation_world.v6`、Store=`gm.store_snapshot.v3`，或项目经过审查的新 schema。
- [ ] 单一 save path，无 GM 默认路径 fallback。
- [ ] 异项目存档不进入 live state。
- [ ] 同进程 reload 未被误记为跨进程恢复。

建立项目自己的 `StudioGame_2D_Debug/Release` 或 `StudioGame_Planar3D_Debug/Release` preset。P27 名称、feature、入口和排除项只是样板证据。输出 EXE/PCK 后，必须先实现项目候选 runner，再按 [构建发布与验收手册.md](构建发布与验收手册.md) 的接口合同验证冷启动身份、actual pack、两个 OS 进程保存/恢复和坏存档；该手册不会把尚不存在的 `--studio-game-*` 当可执行命令。

验收点 H：

- [ ] dependency scan 无 violation/unresolved。
- [ ] 项目自建测试、正式入口和负向合同通过。

- [ ] 真人完成八组 GUI 验收后才宣布最终游戏发布通过。

## 12. 完成定义

垂直切片完成至少意味着：

- 项目身份、Profile、模块和入口一致；
- 玩家/NPC/地图/设施/Task/Process/Ability 形成一条真实事务链；
- UI 只读投影；
- 保存退出与独立恢复通过；
- 坏输入原子拒绝；
- Debug/Release/PCK 从同一源码生成并通过 actual-pack；
- 已披露 Godot 版本、Planar3D 边界、HX1 非 PASS 和未完成人工 GUI 项。

更完整的领域规则见 [GM平台技术手册.md](GM平台技术手册.md)，构建发布细节见 [构建发布与验收手册.md](构建发布与验收手册.md)。
