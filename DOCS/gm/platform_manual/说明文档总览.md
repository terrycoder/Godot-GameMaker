# GM 平台开发文档

本套文档用于让开发者在 GM 平台上搭建具体 Godot 游戏。它描述当前仓库已经实现并经过程序化验证的能力、正确扩展边界和发布流程，不是产品宣传页，也不把中性样板、测试夹具或未完成的真人界面验收当作稳定能力。

## 平台定位

GM 是一套模块化、可裁剪、失败关闭的 Godot 游戏运行时与编辑器工具。核心特点是：

- 业务内容以 Resource 和稳定业务 ID 表达；
- 模块由 Profile、Manifest Index、Manifest 和 Registry 显式选择；
- 玩家、AI、日程与事件统一构造 `GMAbilityActivationRequest`；只有声明领域写入且 `fact_type` 非空的能力才进入 Resolver/Transaction，executor-only/无领域写入能力不得伪造事务；
- `GMSimulationWorld`、领域 Store 和服务分别持有唯一权威；
- UI、场景节点、查询结果和缓存只做投影；
- 保存恢复先离线验证，再做最后一次原子交换；
- 2D 与 Planar3D 共享逻辑平面语义；
- 编辑器 Dock 提供内容制作、校验、Undo/Redo 和保存重开工作流；
- 导出时按模块裁剪，并用正式入口、实际包清单和跨进程证据验收。

## 关键选择

正式候选必须二选一：

- `2D-only`：`core + spatial.core + spatial.planar_2d`；严格排除三维根。
- `Planar3D-enabled`：再加入 `spatial.planar_3d`、`character.visual_3d`、`scene.execution`、`presentation.render_style_3d`、`sample.neutral_vertical`。

Planar3D 是逻辑平面 + Surface Graph + 三维表现，不是任意 Full3D。`gm.spatial.full_3d_reserved` 尚未形成通用发布能力。

## 支持级别标记

文档使用三种标记：

- **已支持**：存在产品实现及当前基线的程序化/合同证据。
- **样板**：可作为结构参考，但必须替换身份、内容和路径；不应原样交付。
- **待人工验收**：机器证据不能代替真人操作、视觉和体验结论。

文中四种“Profile”不是同一对象：`GMProjectProfile` 只选择模块/空间后端；`GMPlayerShellConfiguration` 绑定地图、玩家、内容、相机和保存；`GMNeutralVerticalSampleProfile` 是 EXT10 中性内容编排样板；`GMPlanar3DReleaseProfile` 是 EXT11/P27 发布样板。后两者不是下游稳定 ABI。

## 关键限制

- 当前正式验证基线是 Godot `4.6.2-stable official`；`4.7.2-stable` 未验证。
- P27 封存结论是 `P27_SEALED_GENERALIZED_WITH_AP3_RISKS`；Generalized 不等于 Stable。
- 当前已验收的独立 Planar3D 参考是 CAW-owned 冻结 EXT11 适配；它不是模块中立 PlayerShell SDK。EXT11/2D/P25 父类会重写 Profile 或 Manifest，项目自有 Index 必须由自有 composition root 负责。
- HX1 是 `HX1_RETIRED_PLATFORM_INCOMPATIBLE`，明确不是 PASS。
- 仍有 8 组人工 GUI/真人验收：首次入口与空状态；视觉层级/裁切/缩放；键鼠/手柄/焦点/拖放；2D/3D 目标/相机/HUD 连续性；Definition/中文错误/UndoRedo；编辑器保存重开/引用修复/批量操作；玩家纵向流程反馈；误操作/取消/重试恢复。
- 仍保留 DN-01（surface 一致性诊断）、DN-02（退出期 ObjectDB/resources-in-use）和 TN-01（历史夹具编排修正）。
- 修改冻结核心、入口、Profile、模块选择、schema 或保存隔离后，既有封记不再自动覆盖变更内容。

## 使用原则

1. 项目命名空间与类型前缀分离：实体、角色、流程、事实分别使用 `gm.entity.<namespace>.*`、`gm.actor.<namespace>.*`、`gm.process.<namespace>.*`、`gm.fact.<namespace>.*`；不要写成 `gm.<namespace>.entity.*`，也不要沿用 EXT/P27 样板身份。
2. 从批准的不可变平台版本创建独立项目，不从活动工作区散拷。
3. UI 和 Dock 只提交命令或读取投影，不直接成为领域权威。
4. 所有会改变领域事实的动作走 Ability → Resolver → Transaction；executor-only 能力明确留在执行器路径。
5. 所有保存扩展接入同一个 SimulationWorld 原子恢复边界。
6. 发布同时验证源码、Debug、Release、PCK、正式入口和独立新进程恢复。
7. 机器合同通过后，仍完成八组人工 GUI 验收。

## 文档边界

路径均为仓库相对路径；命令示例使用可替换变量。源码映射只把经过抽核的类和方法标成公共扩展点，其余均标为内部实现、样板、测试或证据。若代码与本文冲突，以当前已审查源码、Manifest/schema 和新一轮正式裁决为准，并更新本文档。

## GitHub 清洁发布版边界

本文件保留平台功能、架构与研究价值；涉及历史测试环境的内容不代表本发布树可直接执行。GitHub 清洁发布版的 CLI 以当前 `gm_cli.gd` 帮助为准，只提供 `help`、`environment`、`compatibility`、`validate`、`modules` 五个只读命令。源仓库内部的测试、插件冒烟、导出冒烟、模块专项验收、GUT、测试目录、fixture、runner 与审查证据均不随本清洁版提供；接收方应在自己的游戏仓库建立测试与发布流水线。
